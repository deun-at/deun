## Answered by the live instance (2026-10-25)
Sources: a public-schema dump of api.deun.app taken 2026-10-24 12:48 (`pg_dump --schema-only --schema=public` plus `pg_get_functiondef` and a tar of `volumes/functions`), kept at supabase/remote_dump/ in the main checkout only (gitignored, because push/index.ts holds a live credential); and read-only catalog queries on 2026-10-25 for what a public-only dump leaves out (publication, replica identity, triggers, image versions, `FUNCTIONS_VERIFY_JWT`).
- RLS and publication: RLS is on for expense, expense_update_checker, friendship, group, group_member, group_update_checker, payment_reminder and user. It is off for device_tokens, expense_entry, expense_entry_share, group_shares_summary and birthday_signup, and every public table has `GRANT ALL … TO anon, authenticated`. Policies: the checker tables, expense and group allow access only when the caller's email is a `group_member` of the row's group (group also by owner `user_id`). friendship allows requester/addressee. group_member has one `FOR ALL TO authenticated USING (true)` policy. user has SELECT/INSERT/UPDATE/DELETE `USING (true)` for every role. No policy filters on `removed_at`. `supabase_realtime` holds exactly group_update_checker, expense_update_checker and friendship, and every public table has default replica identity · answers the RLS/publication item
- Realtime image `supabase/realtime:v2.34.7`, edge runtime v1.66.5, Postgres 15.8. Whether this version accepts AND-combined filters is still unverified; nothing planned relies on it · narrows the realtime-version item
- `device_tokens`: PK `(user_id, token)`, with no unique on `token`, so one device token can be registered for several users, and a signed-out user keeps receiving pushes there. FKs to `auth.users(id)` and `user(user_id)`, both `ON DELETE CASCADE`. No RLS, so an unregister can never be a silent 0-row delete for lack of a policy · answers the device_tokens item and the sign-out ordering item
- `delete-user-account` source recovered: it resolves the caller from the JWT with the service-role client and calls `auth.admin.deleteUser`, nothing else. The cascade `auth.users → user → device_tokens` removes the token rows. **The same cascade also deletes every `expense` the user paid** (`expense.paid_by → user(email) ON DELETE CASCADE`), plus every share, membership, summary row and friendship, so deleting an account silently rewrites other members' balances. No plan covers this · answers the delete-user-account item; new finding
- `push` source recovered (a single index.ts, no sibling files). It builds a service-role client and never inspects the caller, and the instance runs `FUNCTIONS_VERIFY_JWT=false`, so any caller can send any title/body to any email's devices. The FCM service-account key is inlined. It was never in git history: `git log --all -S "BEGIN PRIVATE KEY"` finds nothing. FCM gets data `{type, expense_id: object_id}` plus a `notification {title, body}` block. Tokens come from `user.select('device_tokens(token)').in('email', receivers)`, and an FCM 404 deletes that token's rows. No app trigger, webhook or pg_net call invokes it; the only triggers outside auth/storage/realtime are pgsodium/vault internals · answers the push-contract item
- `claim_set_unit_shares` is live, and so is every function, column and index the pre-dump migrations create. `match_contacts_by_email` is live; it is defined only there. Live but in no migration and called by no client: `pay_back_all` (an unguarded, non-recalculating ancestor of settle-all), `get_group_monthly_statistics`, table `birthday_signup` and enum `"Friendship Status"`. No migration was open in manual-checks at dump time. Live `pay_back` equals the body in 20260816010000 · answers the claim_set_unit_shares item
- Guest merge under RLS: group_member and user are open, expense UPDATE needs the caller to be a member (true once the join's own insert has run), and shares and summary have no RLS. So a SECURITY INVOKER `join_group` can do every write. But **every FK to `user(email)` is `ON DELETE CASCADE`**, not RESTRICT. Deleting a guest's `user` row silently deletes that guest's remaining expenses, shares, memberships and summary rows in every group, because RI actions bypass RLS. Today's client merge already does this: it rewrites shares in every group (no RLS on shares) and then deletes the guest unconditionally. `expense_entry_share` has PK `(expense_entry_id, email)`, so rewriting a guest share onto an entry where the joiner already holds one raises 23505 · answers the guest-merge item; corrects guest-merge-rpc
- Other constraints the plans relied on. `group_member` PK `(email, group_id)` makes a duplicate membership row impossible. `expense_update_checker` and `group_update_checker` cascade from `expense`/`group` and have no DELETE policy, so the client's explicit checker deletes are RLS no-ops today and the cascade does the work. `group.currency_code` is `NOT NULL DEFAULT 'EUR'`, and `user.locale` exists
