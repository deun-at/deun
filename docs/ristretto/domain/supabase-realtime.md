# Supabase Realtime

- **postgres_changes filter limits** An `in` filter accepts at most 100 values. Several filter conditions combine with AND only ("OR is not supported"), so a row that matches on column A or column B needs two subscriptions.
  source: https://supabase.com/docs/guides/realtime/postgres-changes (read 2026-10-22) · unconfirmed — proposed by prep code-review-2026-10, 2026-10-22
- **postgres_changes and DELETE** RLS policies are not applied to DELETE events, so every subscription whose filter matches receives them. A DELETE is matched against the filter on the old row's replica-identity columns: under default identity a filter on a primary-key column (e.g. expense_update_checker.group_id) already receives deletes, and `replica identity full` is needed only to filter on non-key columns. Every other event is authorized against each subscriber, so throughput scales with the number of subscribers.
  source: supabase/schema/baseline.sql realtime.apply_rls :1530-1594, :1748-1760 (live dump 20261025164747), read 2026-10-26; https://supabase.com/docs/guides/realtime/postgres-changes (read 2026-10-22) · unconfirmed — proposed by prep code-review-2026-10, 2026-10-22, updated in prep facts (group-id-leak), 2026-10-26
- **postgres_changes DELETE payload under RLS** On a table with RLS, the live realtime schema sends a DELETE to every subscription whose filter matches the old row, with no RLS check, and trims `old_record` to the primary-key columns the subscriber's role holds column SELECT on. An unfiltered subscriber therefore receives the primary key of every deleted row.
  source: supabase/schema/baseline.sql `realtime.apply_rls` :1726, :1755, :1760 (live dump 20261025164747), read 2026-10-26 · unconfirmed — proposed by prep group-id-leak, 2026-10-26
- **Realtime events follow the publication's publish flags** `realtime.list_changes` passes the `supabase_realtime` publication's insert/update/delete flags to wal2json as `actions`. Publishing without `delete` therefore stops DELETE events for every published table at once. A single table cannot opt out of one event type.
  source: supabase/schema/baseline.sql `realtime.list_changes` :1967–2010 (live dump 20261025164747), read 2026-10-26 · unconfirmed — proposed by prep group-id-leak, 2026-10-26
- **Realtime filters need column SELECT** `realtime.subscription_check_filters` rejects a channel filter on a column that the subscriber's role has no SELECT privilege on ("invalid column for filter").
  source: supabase/schema/baseline.sql `realtime.subscription_check_filters` :2110–2140 (live dump 20261025164747), read 2026-10-26 · unconfirmed — proposed by prep group-id-leak, 2026-10-26
- **Broadcast from the database exists on the live instance** The live realtime schema has `realtime.broadcast_changes`, `realtime.send(payload, event, topic, private default true)` and the partitioned `realtime.messages` table. A trigger can therefore push a change to a private, RLS-authorized channel without publishing the table.
