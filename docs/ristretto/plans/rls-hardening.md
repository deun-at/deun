# rls-hardening — The anon key reaches nothing, and only the people a row concerns can change it

## Spec
- Source: idea — the live-instance answers to code review 2026-10-22 (research/code-review-2026-10.md, "Answered by the live instance (2026-10-25)"), raised by Jakob in review of this prep (2026-10-25)
- Flight: backend-in-repo
- Goal: Nobody without a session can read or write app data. A signed-in user can change only their own rows and the rows of the groups they belong to, and can read group data only for those groups; user profiles and memberships stay readable to every signed-in user. Every flow the app has today keeps working.
- Why: group members and push recipients · noticed by: the web build's public anon key no longer reads every FCM token, share, IBAN or email, and no signed-in stranger can read or rewrite a group's shares, read another user's push tokens, or delete a user (which today cascades away that user's expenses in every group)

## Contract
- Acceptance:
  - [auto] **Anon reaches nothing.** After the new migrations, no public table, view or function remains granted to `anon`, and future tables created in `public` are not granted to it by default. Red means the public anon key in the web build still reads or writes app data. Proven by a source-shape test over the migration files (`revoke … from anon` on all tables and functions in `public`, plus the default-privileges revoke).
  - [auto] **Every app table has RLS.** Each of `device_tokens`, `expense_entry`, `expense_entry_share`, `group_shares_summary` and `birthday_signup` is `enable row level security` in the new migration, and every table already carrying RLS keeps it. `birthday_signup` gets no policy, so it is closed to every client role. Red means a signed-in stranger reads or rewrites rows of groups they are not in. Proven by source shape over the migration plus the table list in research/code-review-2026-10.md.
  - [auto] **Device tokens are private.** device_tokens policies allow select, insert, update and delete only where `user_id = auth.uid()`. Red means any signed-in user reads every device's FCM token, or push-session-lifecycle's sign-out cannot delete its own row. Proven by source shape.
  - [auto] **Expense lines, shares and balances belong to the group.** `expense_entry` and `expense_entry_share` allow every operation only when the caller is a member of the group of the expense they belong to; `group_shares_summary` only when the caller is a member of its `group_id`. Membership counts a soft-removed row, as today's expense and group policies do. Red means a stranger reads or rewrites a group's split, or a member loses access to a past group they still see. Proven by source shape.
  - [auto] **A user row changes only by its owner.** `user` UPDATE is allowed only on the caller's own row (`email` = the session email). INSERT is allowed for the caller's own row or for a guest row (`is_guest` true, email ending `@guest.invalid`). DELETE is allowed only for a guest row that no `group_member` row names. Red means a stranger renames, re-IBANs or deletes another user, and a delete cascades away that user's expenses in every group. Proven by source shape.
  - [auto] **Membership changes only from inside the group, or by joining yourself.** `group_member` INSERT is allowed when the new row's email is the caller's own (an invite-link join, or the creator's own row), or the caller is already a member of that group, or the caller created the group (`group.user_id = auth.uid()`, so `save_group_all` can add the other members of a group it just created). UPDATE and DELETE are allowed only for members of the row's group, and for the caller's own rows. Red means a stranger adds or removes members of any group, or creating a group with members fails. Proven by source shape.
  - [auto] **No recursive policy.** Every policy that asks "is the caller a member of group G" asks it through one SECURITY DEFINER helper with a fixed `search_path`, never through a sub-select on `group_member` inside a `group_member` policy. Red means every query on the table fails with "infinite recursion detected in policy". Proven by source shape.
  - [auto] **Every write the app and its RPCs make today still passes the new policies.** For each client write and each SECURITY INVOKER RPC (`save_expense_all`, `save_group_all`, `claim_set_unit_shares`, `pay_back`, `pay_back_exact`, `update_group_member_shares`, and, where they have landed, `join_group`, `add_group_member`, `remove_group_member`, `delete_group` and `delete_expense`), a table maps the statement to the policy that admits it. The table is kept as data in the test file, and the test pins it against the migration's policy names and the statements found in lib/ and supabase/migrations/. Red means a save, payback, claim, join or member change starts failing with a permission error after Jakob applies the migration.
  - [auto] `dart format`, `flutter analyze` and `flutter test` pass.
  - [human] With the migrations applied on api.deun.app, a request carrying only the anon key reads no row of `device_tokens`, `expense_entry_share` or `user`, and a signed-in account that shares nothing with group G reads no row of G's members, expenses, lines, shares or balances, and cannot update or delete them.
  - [human] With the migrations applied, the everyday flows still work on a real account: sign in on a fresh account (user row created), create a group with a guest, add a member, add and edit an expense in Quick and Itemized, claim a unit, record a payback, settle all with a friend, join by invite link claiming a guest, remove a member, delete an expense and a group, register a push token, sign out.

- Decisions:
  - Scope -> one feature, one migration, no app change (Jakob in review of this prep, 2026-10-25: "one feature", over the offered two-row split; then "signed-in can read all" for reads). The push Edge Function's caller check stays with push-server-compose. The account-delete cascade, which deletes every expense the deleted user paid, is out of scope and recorded as a separate idea (brief).
  - Reads of `user` and `group_member` -> any signed-in user may read every row, and only anon loses access (Jakob, same review: "signed-in can read all"). The accepted exposure: every account can still read every user's email, names, IBAN, PayPal handle and locale, and every group membership. In exchange, stranger search (exact email, name#code, unique username), `match_contacts_by_email` and the join page's guest list keep working in every installed build, and no lookup RPC or client change is needed. Scoping these reads to co-members and friends is a possible later feature, not a pending decision here. The table list "every app table has RLS" holds; these two tables keep RLS with a `TO authenticated USING (true)` SELECT policy, and their UPDATE, INSERT and DELETE policies are the scoped ones in Acceptance.
  - `birthday_signup` -> a dead leftover that nothing in the app reads or writes. It is locked like the rest: RLS on with no policy, and anon revoked. Dropping it is later cleanup, not this feature (Jakob in review of this prep, 2026-10-25: "dead — leave & note it"). schema-baseline lists it as live-only.
  - Membership helper -> `public.is_group_member(_group_id uuid) returns boolean`, SECURITY DEFINER, `stable`, `set search_path = ''`, true when a `group_member` row with the session email exists for that group, soft-removed or not. Parity with the existing policies, none of which checks `removed_at` (research/code-review-2026-10.md, "Answered by the live instance"). It is the only definer function the write half adds, and it reveals one boolean about the caller's own membership.
  - Existing policies -> the policies on expense, expense_update_checker, group, group_update_checker, friendship and payment_reminder stay as they are, except that their `IN (SELECT group_member.email …)` sub-selects keep working unchanged once group_member's SELECT is scoped, because the caller always sees their own membership rows.
  - Guests -> guest rows are created by any member (`createGuest`, `save_group_all`), so INSERT allows a guest row with the `@guest.invalid` domain the app mints (lib/pages/users/user_repository.dart). Deleting a guest is allowed only once no membership names it, which is guest-merge-rpc's rule. Because the user FKs cascade, that rule is also what stops a delete from wiping another group's history.
  - Proof -> SQL by source-shape tests over the new migration files, in the idiom of test/pages/expenses/expense_rate_migration_test.dart. The house rule holds: migrations are authored here and applied by Jakob, so live behaviour is `[human]` (roadmap header; manual-checks.md).
  - (a) per-group currency -> does not apply. No amount, currency or `isSettled` logic is read or written.
  - (b) identity by email -> policies identify the caller by `auth.jwt() ->> 'email'`, the same value `group_member.email` holds, except `device_tokens`, which is keyed by `auth.uid()` as today.
  - (c) soft-removed members -> count as members for read and write, matching today's policies and fetchData's summary join (group-member-removal).
  - (d) guests -> see Guests.
  - (e) en+de ARB strings -> do not apply. No app change, so no string is added or changed.
  - (f) realtime -> realtime authorizes insert and update events against the tables' SELECT policies. Those are unchanged for the three published tables, and group_member's stays open to signed-in users, so subscribers hear what they hear today. Delete events are unaffected (rests on unconfirmed domain/supabase-realtime.md: postgres_changes and DELETE). No publication changes here; realtime-event-scope owns those.
  - (g) test seams -> do not apply. No Dart changes; the proof is source-shape tests over SQL.
  - Old installed builds -> unaffected by design. Every statement they send is one the new policies admit (the statement→policy table), and none of them relies on anon. The migration can be applied as soon as it is authored, and no release has to go out first.
  - Order against the atomic-writes RPCs -> no Depends either way. The statement→policy table covers the client statements and RPC bodies present at build time; for each of guest-merge-rpc, group-write-rpcs and payback-atomic-recalc that has landed, its RPC is in the table, and one that has not is covered by the client statements it will replace. Those plans keep their SECURITY INVOKER rulings, and their source-shape tests are untouched.
  - push-session-lifecycle -> its sign-out unregister deletes `device_tokens` by `user_id` and token, which the owner DELETE policy admits (push-session-lifecycle plan, Decisions "Migrations"). The push function reads and deletes tokens with the service role, which RLS does not apply to.
  - (h) migrations -> authored here, applied by Jakob, an Open manual-checks entry per `[human]` criterion, and a `⚠ migration pending` marker on the row. No client fallback.

## Approach
- Tier: normal — policy design across thirteen tables, a definer helper, and parity with every write the app and its RPCs make leave real judgment to a planner.
- Strategy: one new migration file in three parts (revoke and helper, the five open tables, the user and group_member policies), with no Dart change. Build the statement→policy table first: walk every `.from(…)` write in lib/ and every insert, update and delete inside the RPC bodies in supabase/migrations/ and the RPCs of any atomic-writes plan that has landed. Then write the policies so that every row of the table is admitted, and pin both in one test. The traps are `save_group_all` adding other members to a group whose creator row may not be written first (hence the creator clause), the upsert in lib/auth_gate.dart (INSERT plus UPDATE on the caller's own row), and `update_group_member_shares` deleting and rebuilding summary rows as any member.
- Likely touchpoints: supabase/migrations/ (one new file), test/pages/groups/rls_hardening_migration_test.dart (new), docs/ristretto/manual-checks.md
- Depends: —
- Parallel-with: every other code-review-2026-10 feature except realtime-event-scope, guest-merge-rpc, group-write-rpcs and payback-atomic-recalc, whose migrations it must read at build time (no shared code file; take the next free migration stamp).
