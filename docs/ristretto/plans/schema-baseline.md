## Spec
- Source: idea — code review 2026-10-22 (research/code-review-2026-10.md), architecture item "the base schema lives only in the live DB"; the As-is lines tagged for schema-baseline; Open items "Is `claim_set_unit_shares` live?" and "supabase/config.toml + Docker as the local verification path"

## Contract
- Acceptance:
  - [auto] The rebuild set is the baseline plus exactly the migrations stamped after its dump stamp, replayed in filename order, and a function re-stated after the stamp resolves to its re-stated body. Proven on a fixture with migrations on both sides of the stamp. Against the real tree, none of the 11 migrations present at HEAD 439b7d5 is replayed. Red means a rebuild breaks: replaying `20260417_user_spending_summary.sql` over the baseline's widened `get_user_spending_summary` fails, because create-or-replace cannot change a return type (see the note in `20260628000000`), and skipping a newer file silently drops its change.
  - [auto] The committed baseline holds no row data, meaning no top-level `COPY`, `INSERT` or `setval` outside dollar-quoted function bodies. It also holds no secret: no JWT-shaped token, `Bearer` token literal, URL with embedded credentials, private-key block, password literal or password hash, `jwt_secret` setting value, vault secret literal, or email address outside the `guest.invalid` domain.
  - [auto] The guard flags each of those shapes in planted samples. It passes `pay_back`'s own `insert into expense` body, a `GRANT … TO service_role`, pg_dump's own `\restrict` line and a `guest+…@guest.invalid` literal. A guard that never fires would let a full dump with user rows into git.
  - [auto] Every relation the app reaches through `.from('…')` in lib/ exists in the rebuild set as a table or view. Every function it reaches through `.rpc('…')` also exists there, including `match_contacts_by_email`, which no file in the repo defines today. Red means a rebuilt backend answers a client call with "relation/function does not exist".
  - [auto] The drift check reports a missing target. Given an inline Dart sample that calls an absent RPC and an absent table in the call forms lib/ uses (see Scanner forms), it names both. Given a sample whose targets exist, it reports nothing.
  - [auto] Every table the app subscribes to through `subscribeToChannel(table: …)` is a member of the `supabase_realtime` publication in the rebuild set. Today those tables are `group_update_checker`, `expense_update_checker` and `friendship`. Red means a rebuilt backend accepts writes but never pushes the live refresh.
  - [auto] Every function, added column and index created by a migration stamped before the dump exists in the rebuild set. That makes the live status of `claim_set_unit_shares` a test result instead of a guess.
  - [human] On api.deun.app, every object re-stated by a reconciliation migration from this feature exists after Jakob applies that migration. This is vacuous, with no manual-checks entry, when the dump shows no gap.
  - [auto] `dart format`, `flutter analyze` and `flutter test` pass. Already enforced by test/pages/expenses/expense_rate_migration_test.dart (pins `20260816020000`'s content, that `20260618000000` carries no provenance column, and the multi-currency-expense-rate entry above `## Applied` in manual-checks) and test/docs/ristretto_links_test.dart (every relative `.md` link under docs/ristretto resolves); both must stay green.
- Provides:
  - `supabase/schema/baseline.sql`: the reference schema. Its header carries a machine-readable `-- dump-stamp: YYYYMMDDHHMMSS` line.
  - `RebuildSet.load({String baselinePath = 'supabase/schema/baseline.sql', String migrationsDir = 'supabase/migrations'}): RebuildSet`, in test/supabase/rebuild_set.dart (test-only library, imported by relative path).
  - `RebuildSet.dumpStamp: String`, `RebuildSet.replayedMigrations: List<String>`
  - `RebuildSet.hasRelation(String name): bool`, `RebuildSet.hasFunction(String name): bool`, `RebuildSet.hasColumn(String table, String column): bool`, `RebuildSet.hasIndex(String name): bool`, `RebuildSet.inRealtimePublication(String table): bool`
  - `RebuildSet.latestFunctionSource(String name): String?`: the newest definition, where a replayed migration wins over the baseline. Later SQL source-shape tests assert new RPCs against this.
  - Top-level in the same library: `findDataStatements(String sql): List<String>`, `findSecrets(String sql): List<String>` (the offending snippets, empty when clean); `clientRelations(String dartSource): Set<String>`, `clientRpcs(String dartSource): Set<String>`, `clientRealtimeTables(String dartSource): Set<String>`

- Decisions:
  - Baseline location -> supabase/schema/baseline.sql, a reference file kept outside the dated chain because the live DB already contains every incremental migration; existing migrations stay as history (Jakob in prep code-review-2026-10 (2026-10-24)). The path is not covered by the `supabase/schema.sql` line in .gitignore. CI (pr_checks.yml) runs `flutter test`, so an untracked baseline goes red there.
  - Source -> a schema-only pg_dump of api.deun.app that Jakob supplies, never generated here. The deployment is custom Docker, so there is no Supabase CLI and no local database, and the house rule (authored here, applied by hand) stays (Jakob in prep code-review-2026-10 (2026-10-24)).
  - Scope -> the whole database with no schema filter. A schema-filtered dump omits publications and their membership, which the brief counts as base schema; only an unfiltered one brings `supabase_realtime` membership, replica identity, and any app trigger or policy outside `public`. The README marks which parts the app owns and which a fresh Supabase stack already provides (Jakob in prep code-review-2026-10 (2026-10-24); research/code-review-2026-10.md As-is: no publication or trigger anywhere in supabase/migrations/).
  - Verbatim -> committed exactly as dumped, with a header added on top. The only permitted edit is a redaction: each one is replaced by a named placeholder and listed in the header (precedent: supabase/migrations/20260815000000_baseline_ledger_functions.sql, which kept known defects and improved nothing; research/code-review-2026-10.md As-is for schema-baseline).
  - Header -> source (api.deun.app, self-hosted Docker), `dump-stamp`, "schema-only, no data", scope, pg_dump's own server-version line, the redaction list, and a pointer to supabase/schema/README.md (Jakob in prep code-review-2026-10 (2026-10-24): source, dump date, schema-only).
  - Dump stamp -> the date and time the dump was taken, as Jakob reports it. The dump is taken with no migration open in manual-checks, so "stamped before" means the same as "contained". A violation shows up as missing objects in the chain-coverage criterion (Jakob in prep code-review-2026-10 (2026-10-24): rebuild = baseline + migrations dated after the dump).
  - Rebuild order -> a fresh self-hosted Supabase stack, then the app-owned parts of the baseline, then the migrations stamped after the dump stamp, in filename order. A short stamp like `20260417` pads with zeros. The README states the same rule RebuildSet implements, plus two more: every later migration must be stamped after the dump stamp (one stamped earlier is neither replayed nor in the dump, and chain coverage goes red), and a newer dump replaces the file wholesale and moves the stamp (Jakob in prep code-review-2026-10 (2026-10-24)).
  - Gap remedy -> applies if the dump lacks an object a pre-stamp migration creates, or a subscribed table sits outside `supabase_realtime`. The fix is one new migration stamped after the dump that re-states only the missing objects, each in the newest form the chain gives it. Never re-state a whole old file: `20260618000000`'s `save_expense_all` predates the provenance columns. The migration is authored here, not applied, and gets an Open manual-checks entry. No client fallback is added for it, and no test allowlist is used. The result answers the research Open item about `claim_set_unit_shares` for legacy-fallback-removal. Two cases are not gaps. An object whose migration was still open in manual-checks when the dump was taken means the dump came too early: Jakob applies it and dumps again, and the Blockers line returns. A client target that neither the dump nor any migration defines (only `match_contacts_by_email` can be one) has no source to restate, so it is recorded under manual-checks Findings and the build stops for Jakob (roadmap house rule; research/code-review-2026-10.md Open item on `claim_set_unit_shares` and As-is line on `match_contacts_by_email`).
  - realtime-event-scope -> no Depends either way, and the two do not run in parallel. It subscribes to a fourth table, `group_member`, and authors a migration that adds it to `supabase_realtime` through a plain `ALTER PUBLICATION … ADD TABLE` inside a guard, and sets replica identity full on `group_update_checker` and `friendship`. If it has landed first, the publication criterion covers `group_member` too: its migration is applied before the dump is taken (Dump stamp), so the dump carries the membership. If this lands first, its migration is stamped after the dump and `RebuildSet` replays it, so the scanner sees the add. Because that add sits inside a guard block, the publication parse counts an `ALTER PUBLICATION … ADD TABLE` inside a `DO` block's dollar-quoted body as membership (unlike the data scan, which skips those bodies), pinned by a fixture sample. The scanner stays a pure reader in both orders (realtime-event-scope plan, Decisions "Migration shape" and "schema-baseline interplay").
  - Publication forms -> explicit membership counts, whether written as `ALTER PUBLICATION … ADD TABLE` or `CREATE PUBLICATION … FOR TABLE`, and so does a `FOR ALL TABLES` publication (research/code-review-2026-10.md Open item on `supabase_realtime` membership).
  - Reference role -> once this lands, SQL source-shape tests for new RPCs check against `RebuildSet` instead of a single migration file (Jakob in prep code-review-2026-10 (2026-10-24)). Precedent for proving server code by its source: test/pages/expenses/exchange_rate_function_test.dart (multi-currency-rate-source). The atomic-writes siblings (guest-merge-rpc, payback-atomic-recalc, group-write-rpcs) read their own migration files and do not depend on this feature (their prep ruling). Their tests stay valid afterwards, because their files stay in supabase/migrations/ and the baseline sits outside that folder. Their migrations, like any other, are applied before the dump is taken (see Dump stamp).
  - Helper location -> test/supabase/, as a test-only library. lib/ does not change, because nothing the app ships reads SQL (precedent: test/pages/expenses/exchange_rate_function_test.dart reads server source from test/, multi-currency-rate-source).
  - Name matching -> case-insensitive. An unqualified name means `public`. Quoted identifiers are unquoted, since pg_dump writes `public."group"` and `public."user"`, as the chain itself does (supabase/migrations/20260610120000_atomic_save_rpcs.sql). Both `CREATE` and `create or replace` forms count.
  - Privacy guard -> runs on Jakob's file in the working tree before anything under supabase/schema/ is staged, because a secret that reaches git history stays there after a later redaction. The data scan skips dollar-quoted bodies, because `pay_back` legitimately inserts. Secrets are matched by named shapes, not by entropy, so pg_dump's `\restrict` nonce and `GRANT … TO service_role` do not trip it. The shapes include password literals and hashes (user-mapping options, role passwords) and a `jwt_secret` setting, which a self-hosted Supabase database can carry. `@guest.invalid` emails are allowed. The likeliest real hit is a webhook trigger that carries the service-role JWT, which gets redacted (Jakob in prep code-review-2026-10 (2026-10-24): no COPY/INSERT data, no secrets, keys or vault values).
  - Drift scope -> names only, checked against the rebuild set, which at build time is the baseline itself; a later client call to an RPC added by a post-dump migration passes without refreshing the dump. A `.from` target can be a table or a view; an `.rpc` target must be a function. Parameter names stay with each RPC's own test (`payBackRpcParams` in test/model/group_repository_test.dart) (Jakob in prep code-review-2026-10 (2026-10-24): every `.from` table and `.rpc` function, `match_contacts_by_email` included).
  - Scanner forms -> every `.dart` file under lib/, single or double quotes. The name can sit on the line after `rpc(`, as it does at 13 of the 17 rpc call sites in lib/ at HEAD 439b7d5. Requiring a string literal skips calls like `List.from(x)`.
  - Edge Functions -> out of scope, because pg_dump does not contain them. `push` belongs to push-server-compose. `delete-user-account`, `send-contact-email` and `parse-receipt` are listed in the README as not rebuilt from the repo (research/code-review-2026-10.md As-is on supabase/functions/).
  - RLS and policies -> captured verbatim but not asserted. A gate that goes red on a live policy gap has no safe automatic fix, since turning on RLS without policies locks users out. realtime-event-scope reads them from the baseline (research/code-review-2026-10.md Open item on RLS and `supabase_realtime` membership).
  - supabase/config.toml -> deleted. Only the Supabase CLI reads it, and Jakob ruled the CLI out. It also advertises a local reset that would replay the chain onto an empty database and fail at `20260417` (no tables), and it seeds a `seed.sql` that does not exist. It holds no secrets (only env() references), and git history (ff4a227) keeps it. This closes the research Open item about config.toml + Docker (Jakob in prep code-review-2026-10 (2026-10-24): no CLI, no local database; research/code-review-2026-10.md As-is on config.toml).
  - Ignore files -> the .gitignore lines `supabase/schema.sql`, `supabase/seed.sql`, `supabase/push.ts` and supabase/.gitignore stay, because they may shield local files that hold data or secrets (.gitignore at HEAD 439b7d5).
  - manual-checks -> the baseline itself needs no apply, since it is the live state. It gets one Applied-table row ("reference dump, nothing to apply"), following the `20260815000000` row. Edits are additions only: the multi-currency-expense-rate entry stays above `## Applied`, where expense_rate_migration_test pins it (docs/ristretto/manual-checks.md Applied table at HEAD 439b7d5).
  - Cross-cutting -> (a) per-group currency and isSettled: no money logic changes; currency applies only through chain coverage of `group.currency_code` and the five provenance columns. (b) identity by email: no identity logic changes; the privacy guard treats every email literal outside `guest.invalid` as personal data. (c) soft removal: `group_member.removed_at` is covered by the chain-coverage criterion. (d) guests: the guard allows `guest.invalid`. (e) en+de ARB strings: none, no user-facing text. (f) realtime checker bumps: this feature adds no write, so nothing new must bump a checker; the publication criterion covers the checker tables' membership. (g) function-typed test seams: do not apply; fixture tests run over pure helpers. (h) migrations: the baseline is not a migration; a reconciliation migration, if any, is authored not applied and gets no client fallback (roadmap house rule).

## Approach
- The work is one file Jakob supplies plus the tests that make it trustworthy; lib/ does not change. Apart from the dump, its README and the config.toml removal, everything is test-only Dart under test/supabase/. One small library, `RebuildSet`, parses the baseline and the later migrations into relations, columns, functions (with their newest source), indexes and publication members, and provides the two scans: data and secret shapes in SQL, call targets in Dart.
- Privacy comes first: the guard is built and run on the dump in the working tree before the dump is staged, so nothing secret enters git history. Redactions are listed in the header.
- Build the rest fixture-first. Every parsing rule (stamp padding, quoted and unqualified identifiers, publication forms, dollar-quoted bodies, names on the line after `rpc(`) gets an inline sample before it touches the real dump, so a real-file criterion can only go green because the real file passes, not because a scanner found nothing.
- Then the real-file drift (with realtime) and chain-coverage checks. If either fires, the dump has shown something the repo did not know (most plausibly `claim_set_unit_shares` was never applied); the remedy is the single reconciliation migration from Decisions, never an allowlist.
- The README, the config.toml removal and the manual-checks row come last.
- Tier: normal — the SQL parsing rules, the secret shapes and the gap remedy leave real judgment to a planner, and the outcome depends on a dump nobody has seen yet.
- Likely touchpoints: supabase/schema/baseline.sql (new), supabase/schema/README.md (new), supabase/config.toml (deleted), test/supabase/rebuild_set.dart (new), test/supabase/rebuild_set_test.dart, test/supabase/schema_baseline_privacy_test.dart, test/supabase/schema_baseline_drift_test.dart, docs/ristretto/manual-checks.md, and a new supabase/migrations/ file only on a gap. The scanner reads every `.dart` file under lib/ without editing any; today the targets sit in the repositories under lib/pages/*/data/, lib/pages/users/user_repository.dart, lib/pages/groups/presentation/group_join_page.dart, lib/navigation.dart, lib/auth_gate.dart, lib/helper/helper.dart, the two notifiers under lib/pages/statistics/provider/ and the five realtime providers.
