# push-session-lifecycle — Push registration lives and dies with the signed-in session

## Spec
- Source: idea — code review 2026-10-22 (research/code-review-2026-10.md), findings 4 + 5 (stacked FCM listeners; sign-out and account delete never remove the device token)
- Flight: review-bugs
- Goal: A signed-out device stops receiving its previous user's pushes, and one notification tap navigates once however often users sign in and out.
- Why: push recipients · noticed by: no push on a device after its user signed out; text arrives in the receiver's language; only members of a shared group can be targeted

## Contract
- Acceptance:
  - [auto] One notification tap opens its target exactly once, and one token refresh registers exactly once, however often the session restarted within one app run: after sign-out then sign-in, after the main screen starts the session again for the same user, and after a different user's session starts with no sign-out in between (fake messaging with broadcast streams; open-handler and register calls counted).
  - [auto] Once the session has ended, whether through the app's sign-out or through a signedOut auth event the app did not start (for example an expired session), a notification tap opens nothing and a token refresh registers nothing.
  - [auto] Starting a session registers this device's token for the signed-in user exactly once. A token refresh during the session registers the new token for that same user, and a later sign-out removes the refreshed token, not the replaced one.
  - [auto] Signing out deletes the device_tokens row matching the signed-in user's id and this device's registered token, and that delete finishes before the auth session is ended (call order recorded by fakes).
  - [auto] Sign-out still ends the auth session and raises no error when removing the token throws, and still ends it within 3 s when removing the token never completes.
  - [auto] When the messaging layer reports that pushes cannot work on this device, a session registers no token and subscribes to nothing. Sign-out then attempts no delete and raises no error.
  - [auto] Signing out while the session is still starting (permission prompt or token fetch unresolved) leaves no token registered and no listener active once that start finishes.
  - [auto] A notification that cold-started the app opens once per launch. It does not open again when the user signs out and back in during that launch.
  - [auto] Confirming Sign out in Settings removes this device's token and then signs out, through the same sign-out that account delete uses (widget test over the Settings screen with that sign-out faked).
  - [auto] Deleting the account removes this device's token and signs out, through that same sign-out, only after the `delete-user-account` call has succeeded. When that call fails, the user stays signed in, the token stays registered and the existing account-delete error snackbar shows (widget test over the delete sheet with the Edge Function call faked).
  - [auto] Notification routing by data keys is unchanged: type 'group' targets the group whose id is in data['expense_id'], 'expense' targets the expense read view for data['expense_id'], 'friendship' targets the friends tab, and any other or missing type (including 'reminder') targets nothing (unit test). Where each target then lands is already enforced by test/helper/navigate_to_expense_test.dart ('a cold-start notification opens the read view, not the editor' and the other five navigateToExpense cases, 'a group notification still opens the group detail', 'a friendship notification still opens the friends tab'), which must stay green.
  - [auto] Deep links keep their allowlist. These are accepted: /group/join with a UUID groupId; /friend/accept with a valid email or with a username plus code; /group, /friend, /setting, /setting/privacy-policy and /setting/contact. Every other path (including /dev/gallery and /group/details) and every malformed parameter is rejected (unit test).
  - [auto] Signing in as another account still shows none of the previous user's data, and device preferences survive. This is already enforced by test/provider/auth_switch_invalidation_test.dart ('signedOut invalidates the user-scoped providers (user detail, group list, friendship list) so they refetch', 'signedOut leaves device-scoped preference providers untouched', 'signedIn as a DIFFERENT user invalidates; the same user does not'), which must stay green with those cases unedited.
  - [auto] `dart format`, `flutter analyze` and `flutter test` pass.
  - [human] On a physical device, after user A signs out in Settings, A's device_tokens row for the device's token is gone and a push addressed to A no longer arrives there. After B signs in on that device, B's push arrives and tapping it opens its target once.
  - [human] After an account is deleted on a physical device, no device_tokens row remains for that user and the device's token.
- Provides:
  - `abstract interface class PushMessaging` with `prepare(): Future<bool>` (requests permission and, on iOS, checks once for an APNS token; false when permission is denied, on web, or when iOS returns no APNS token, exactly today's gating), `getToken(): Future<String?>`, `getInitialMessage(): Future<RemoteMessage?>`, `onMessageOpenedApp: Stream<RemoteMessage>` and `onTokenRefresh: Stream<String>`. The app's implementation is `FirebasePushMessaging implements PushMessaging`.
  - `abstract interface class DeviceTokenStore` with `register({required String userId, required String token}): Future<void>` and `unregister({required String userId, required String token}): Future<void>`. The app's implementation is `SupabaseDeviceTokenStore implements DeviceTokenStore`.
  - `pushMessagingProvider: Provider<PushMessaging>` and `deviceTokenStoreProvider: Provider<DeviceTokenStore>`, both keepAlive and overridable in tests.
  - `class PushSession`, a keepAlive generated notifier with state `void`, reached through `pushSessionProvider.notifier`. It has `start({required String userId, required PushOpenHandler onOpened}): Future<void>`, `end(): Future<void>` and `registeredToken: String?`. `typedef PushOpenHandler = Future<void> Function(RemoteMessage message)`.
  - `sealed class PushTarget` with `PushGroupTarget(String groupId)`, `PushExpenseTarget(String expenseId)` and `PushFriendsTarget()`. `pushTargetFor(Map<String, dynamic> data): PushTarget?`, and `openPushMessage(RemoteMessage message, GlobalKey<NavigatorState> rootNavigatorKey): Future<void>`, which logs failures and never throws.
  - `signOutUser({required PushSession push, required Future<void> Function() authSignOut, Duration tokenRemovalTimeout = const Duration(seconds: 3)}): Future<void>`. Also `typedef AppSignOut = Future<void> Function()` and `appSignOutProvider: Provider<AppSignOut>`, the one sign-out every surface calls.
  - `validateDeepLink(String fragment): String?` and `listenToDeepLinks(GlobalKey<NavigatorState> rootNavigatorKey): StreamSubscription<Uri>`.
  - `showDeleteAccountSheet(BuildContext context, {AccountDeleter? deleteAccount}): void`, with `typedef AccountDeleter = Future<void> Function()`.

- Decisions:
  - Who owns the push lifecycle -> one keepAlive Riverpod `PushSession` owns FCM permission, token registration and the onMessageOpenedApp, onTokenRefresh and getInitialMessage handling. NavigationScreen only calls `start` from the post-frame callback where `_initFirebaseMessaging` runs today. Source: Jakob in prep code-review-2026-10 (2026-10-24) (brief ruling); research/code-review-2026-10.md (navigation.dart `_handlePush`, auth_gate.dart).
  - Exactly one listener of each kind at any time -> `start` does nothing if a session is already running for the same user, and cancels any existing subscriptions before subscribing for a different user. `end` and provider dispose cancel them. `end` is idempotent: a second call while one runs awaits the same removal and a later call does nothing, so a double tap on Sign out deletes once. Source: Jakob in prep code-review-2026-10 (2026-10-24) (brief ruling); idempotent `end` is a prep ruling.
  - Sign-outs the app did not start (expired session, revoked refresh token) -> the push session is per-user keepAlive state, so it joins `invalidateUserScopedProviders`, and its onDispose cancels the subscriptions. This applies the auth-switch-stale-providers ruling that "any other keepAlive provider holding per-user state found during implementation joins the list" and does not change it. No row can be deleted there because the session is already gone; that gap is accepted. Source: archived auth-switch-stale-providers plan.
  - One app sign-out -> `signOutUser` first unregisters this device's token while the session still exists, by deleting the device_tokens row matching the session's user_id (the signed-in user's id, since `start` re-registers on a user change) and its registered token. Matching on both columns is correct whichever of the two possible PKs the table has. It then calls supabase signOut. Settings sign-out and account delete both go through `appSignOutProvider`. Source: Jakob in prep code-review-2026-10 (2026-10-24).
  - Token-delete failure -> a failure never blocks sign-out. It is only logged (debugPrint) and never shown to the user. The token removal is bounded at 3 s so that an offline device can still sign out. Source: Jakob in prep code-review-2026-10 (2026-10-24) for never blocking; the 3 s bound is a prep technical ruling.
  - Provider invalidation -> stays in `AuthUserSwitchListener` (lib/provider.dart), and `signOutUser` invalidates nothing. `signOutUser` is the one place for side effects that must run before sign-out; the listener cannot host the token delete, because the signedOut event arrives after the session is gone. Source: Jakob in prep code-review-2026-10 (2026-10-24).
  - Account delete order -> invoke `delete-user-account` first and call the app sign-out only once it has succeeded. Unregistering first would leave a user whose deletion failed signed in but without pushes. If a restricting FK from device_tokens existed, it would already break account deletion for every user with a registered device, so deleting the row afterwards cannot newly break it. Whether the still-held JWT authorizes that delete is manual check 2. Source: prep ruling; research/code-review-2026-10.md Open (delete-user-account source not in the repo).
  - Which token is deleted -> the token this session registered or last refreshed to. A session that registered none deletes nothing. A row left by an earlier grant on a device where permission is now denied is out of scope. Source: prep ruling.
  - Start/end race -> `end` lets an in-flight `start` settle within the same 3 s bound. A `start` that finishes after `end`, or after the provider was disposed, registers nothing and subscribes to nothing (generation check after every await; dispose bumps the generation too). The session takes its messaging and store once in build and never touches `ref` after an await, because Riverpod 3 rejects use of a disposed Ref. Source: prep ruling.
  - Cold start -> getInitialMessage is handled at most once per app process, whatever the plugin returns on later calls. The handled flag lives outside the session's own state, because the session is rebuilt after every sign-out. Source: prep ruling.
  - Platform gating -> unchanged from today, and it moves verbatim into `FirebasePushMessaging.prepare`: permission is requested on every platform as today; then denied permission, web (the kIsWeb branch is empty today) and an iOS device whose single `getAPNSToken` call returns null all register and subscribe nothing, with no retry. No test can reach this mapping (no Firebase messaging harness); it is lifted unchanged and manual check 1 observes it on the device used. Source: research/code-review-2026-10.md (navigation.dart rows).
  - Token refresh -> registers the new token for the session's user. The replaced token's row stays, because FCM rejects a rotated token and server-side cleanup belongs to push-server-compose. Source: prep ruling.
  - device_tokens write shape -> `register` keeps today's upsert of {user_id, token} without onConflict, because the PK is unknown. Identity here stays the auth user id, as today, and not the email (dimension b: the push function maps receiver emails to tokens server-side, unchanged). Source: research/code-review-2026-10.md.
  - Migrations (dimension h) -> none are authored and no RPC is added, so the legacy-fallback question does not arise. The delete runs through PostgREST under the existing device_tokens RLS, which only the live instance knows. PostgREST reports success on a 0-row delete, so a missing owner DELETE policy can only show up in manual check 1. Its remedy would be a follow-up migration, not part of this row. The roadmap row gets no ⚠ migration pending marker. Source: roadmap header (authored-not-applied rule); research/code-review-2026-10.md Open.
  - Push data keys -> unchanged: data['type'] and data['expense_id'], where for 'group' the expense_id carries the group id. 'reminder' still opens nothing, because push-server-compose owns that. Source: Jakob in prep code-review-2026-10 (2026-10-24) (brief ruling); research/code-review-2026-10.md.
  - Test seams (dimension g) -> FirebaseMessaging sits behind `PushMessaging` and device_tokens behind `DeviceTokenStore`, both supplied through overridable providers. The widget call sites get `appSignOutProvider` plus an `AccountDeleter` parameter on the delete sheet, in the function-typed override style of ExpenseSaver, PaybackRecorder and notifyOverride. The signedOut-event case needs `AuthUserSwitchListener`, whose build reads `supabase.auth.currentUser`, so it runs in the harness of test/provider/auth_switch_invalidation_test.dart (Supabase initialised against localhost, no network). Source: Jakob in prep code-review-2026-10 (2026-10-24) (brief ruling).
  - File split -> push code moves to lib/push_notifications.dart, deep-link code to lib/deep_links.dart and the sign-out to lib/pages/auth/sign_out.dart. Routes, the GoRouter, `_initUserLocale` and the lifecycle observer stay in lib/navigation.dart, because test/widgets/screen_transition_test.dart reads that file's source and must stay green. typed-routes moves the routes later. Source: CODE_REVIEW_2026-07-07 §6 via research/code-review-2026-10.md; Jakob in prep code-review-2026-10 (2026-10-24) (brief ruling).
  - Deep-link subscription -> stays owned by NavigationScreen: started after the first frame and cancelled in dispose, which is already correct. Only the validation and listening code move. Source: research/code-review-2026-10.md.
  - Realtime (dimension f) -> does not apply. The paused → `removeAllChannels` lifecycle code stays in navigation.dart untouched; realtime-channel-lifecycle leaves it unchanged too (its Decisions, "App pause"), so the two share no code. Source: realtime-channel-lifecycle plan.
  - Currency (a) and soft-removed members (c) -> do not apply: no money and no membership is read. Guests (d) -> do not apply: guest members (is_guest, guest+...@guest.invalid from lib/pages/users/user_repository.dart) never sign in, so they never hold a session or a token. Source: prep ruling.
  - Locale (e) -> no new user-facing string, because token failures are only logged and the account-delete failure reuses `deleteAccountError`. No ARB change. Source: prep ruling.
  - injectable-repositories -> no Depends either way. Its allowlist names lib/push_notifications.dart and lib/pages/auth/sign_out.dart as push plumbing once this lands, and the push registration in lib/navigation.dart and the two settings `signOut()` calls before it. If it has landed first, NavigationScreen takes the user id it passes to `start` from `currentUserProvider` instead of reading `supabase.auth`, and `SupabaseDeviceTokenStore` and `appSignOutProvider` keep using the global client, which that plan leaves out of scope for device_tokens and auth plumbing. Source: injectable-repositories plan, Decisions "Single reader of auth" and "Global client outside repositories".
  - Out of scope -> the `notifications_enabled` preference still does not gate FCM. The Settings sign-out dialog gets no new busy state, because the 3 s bound caps the wait. The background handler in lib/main.dart is left to housekeeping. Sources: lib/provider.dart (`kNotificationsEnabledPrefKey` doc); housekeeping plan; prep ruling (no busy state).

## Approach
- Tier: normal — a keepAlive session with a start/end race, a generation guard and a cold-start flag that outlives it, plus a new sign-out wired into two settings surfaces, leave real sequencing and harness choices for a planner.
- Build from the bottom up so that every piece is testable without Firebase or Supabase. Lift today's push code out of `_NavigationScreenState` into lib/push_notifications.dart. Permission, the iOS APNS check, the web skip, the vapid key and setAutoInitEnabled become `FirebasePushMessaging`. The upsert becomes `SupabaseDeviceTokenStore.register`, next to a new `unregister` that deletes by user_id and token. `_handleMessage` splits into the pure `pushTargetFor` and `openPushMessage`, which resolves its context from the root navigator key it is handed, so no State is captured.
- `PushSession` holds the user id, the registered token, the two subscriptions and a start-generation counter; the cold-start flag lives outside it. `ref.onDispose` cancels the subscriptions, and the provider joins `invalidateUserScopedProviders`, which covers sign-outs the app never started. In NavigationScreen's post-frame callback, `_initFirebaseMessaging()` becomes a `start` call with the current user id and an `openPushMessage` handler over `_rootNavigatorKey`. With no user signed in, nothing starts.
- `signOutUser` runs `push.end()` inside a 3 s timeout and a catch that only logs, then calls the auth sign-out. `appSignOutProvider` wires in the real session and `supabase.auth.signOut`. Settings and the delete sheet read that provider. The delete sheet keeps its existing catch and snackbar, and only reaches the sign-out after the Edge Function call has succeeded.
- Deep links move last and change no behaviour. NavigationScreen still owns `_linkSubscription` and cancels it in dispose. Routes stay in navigation.dart.
- Regenerate the Riverpod code for the new providers. Append the two Manual-Checks entries under Open in docs/ristretto/manual-checks.md. No migration is authored.
- Not parallel with typed-routes or housekeeping (both edit lib/navigation.dart), push-server-compose (owns the push data keys that move here), helper-split (the navigate helpers this calls) or injectable-repositories (settings and auth reads).
- Likely touchpoints: lib/navigation.dart, lib/push_notifications.dart (new), lib/deep_links.dart (new), lib/pages/auth/sign_out.dart (new), lib/provider.dart and lib/provider.g.dart, lib/pages/settings/setting.dart, lib/pages/settings/settings_sheets.dart, test/push_notifications_test.dart (new), test/deep_links_test.dart (new), test/pages/auth/sign_out_test.dart (new), test/provider/auth_switch_invalidation_test.dart (one new case), test/widgets/setting_page_test.dart, test/widgets/settings_sheets_test.dart, docs/ristretto/manual-checks.md
