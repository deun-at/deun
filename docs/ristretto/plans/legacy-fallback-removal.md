# legacy-fallback-removal — Writes commit through their RPC or fail, with no client-side fallback

## Spec
- Source: idea — code review 2026-10-22 (research/code-review-2026-10.md), architecture item "legacy client write paths duplicate server logic without transactions"; the As-is lines tagged for legacy-fallback-removal; Open item "Is `claim_set_unit_shares` live?"
- Flight: backend-in-repo
- Goal: Every non-transactional client fallback whose RPC the live schema dump proves present is deleted, so a group save, expense save, payback or claim either goes through its server RPC or fails visibly, never through a client-side multi-step write.
- Why: Jakob as sole maintainer · noticed by: the backend rebuilds from supabase/migrations/, the fallback code paths are gone, the 1500–1900-line files open in pieces

## Contract
- Acceptance:
  - [auto] When `save_group_all` fails with a missing-function error (PGRST202 or 42883), `GroupRepository.saveAll` throws that same error and nothing else reaches the server: no `group` upsert, no `group_member` write, no `update_group_member_shares`. When the RPC succeeds, `saveAll` returns the id the RPC returned, after that one call. Red means a group save that should have failed half-writes outside a transaction (a group row with no members), or a successful save opens the wrong group. Red at HEAD, where `_saveAllLegacy` runs.
  - [auto] When `save_expense_all` fails with a missing-function error, `ExpenseRepository.saveAll` throws that same error and nothing else reaches the server: no `expense`, `expense_entry` or `expense_entry_share` write, no `update_group_member_shares`. When the RPC succeeds on an edit, `saveAll` completes after that one call. Red means a save that should have failed half-writes outside a transaction: the old path deletes every line of the expense before re-inserting them one at a time, so a failure part-way loses lines, and it silently drops the original currency and rate. Red at HEAD.
  - [auto] When `pay_back_exact` fails with a missing-function error, `GroupRepository.payBack` throws that error after that one RPC: no `pay_back`, no `update_group_member_shares`. A second `payBack` afterwards again issues `pay_back_exact` alone. Red means a payback is recorded through plain `pay_back` at the client-rounded amount, which brings back the sub-cent residue that settle-residue removed (a wrong balance), or a whole session keeps using that path after one failed probe. Red at HEAD.
  - [auto] Only when the baseline defines `claim_set_unit_shares` (see Decisions): when it fails with a missing-function error, `ExpenseRepository.claimSetUnitShares` throws that error and nothing else reaches the server (no share delete or insert, no recalculation). A claim change that fails shows the claim screen's existing error SnackBar and leaves the unit's chips as they were. Red means a claim change deletes a unit's claimers and then fails before re-inserting them, so claims are lost. When the baseline lacks it, the claim path is unchanged and this criterion has no test.
  - [auto] Every RPC whose fallback this feature deletes is defined in supabase/schema/baseline.sql itself, read with no migrations replayed after it. Expected, from the manual-checks Applied table: `save_group_all`, `save_expense_all` and `pay_back_exact`, plus `claim_set_unit_shares` exactly when its fallback is deleted. Red means the app has lost its fallback for an RPC the live instance was never shown to have, so that write fails for every user.
  - [auto] A failed group save or payback still reaches the user as that screen's existing error SnackBar, with the button back to idle and no check. Already enforced by test/widgets/group_edit_screen_test.dart ("a failed save keeps its error, stays put and shows no check") and test/widgets/record_payback_sheet_test.dart ("an unexpected write failure keeps the generic error"); both must stay green.
  - [auto] A failed expense save still raises the editor's existing save-error SnackBar and never shows a check. The never-a-check half is already enforced by test/widgets/expense_save_status_test.dart ("a failed save shows the error and never shows a check"), which must stay green; at HEAD that test does not assert the SnackBar. The SnackBar half is new here, unless editor-failure-keeps-form (whose first criterion asserts it) has landed first. Red means a save that failed on a missing RPC closes with no word to the user.
  - [auto] Every RPC and relation the app still calls exists in the rebuild set. Enforced by schema-baseline's drift criterion, whose test (test/supabase/schema_baseline_drift_test.dart) arrives with that dependency and must stay green.
  - [auto] `dart format`, `flutter analyze` and `flutter test` pass. test/model/group_repository_test.dart (the `payBackRpcParams`, `planPayBack` and `resolveSaveMembers` groups) and test/docs/ristretto_links_test.dart stay green unchanged.

- Decisions:
  - Which fallbacks go -> each one whose RPC supabase/schema/baseline.sql defines. One whose RPC the baseline lacks stays, and that is recorded in this plan's Evidence and on the roadmap row (Jakob in prep code-review-2026-10 (2026-10-24)). The first three criteria are written for the expected case; any of them whose RPC the dump lacks is dropped and recorded the same way, exactly as the fourth is for the claim RPC. The expected outcome follows the manual-checks Applied table: `save_group_all` and `pay_back_exact` (2026-08-16) and `save_expense_all` (2026-09-11) are applied. `claim_set_unit_shares` is evidenced only by a test comment (research/code-review-2026-10.md, As-is and Open item).
  - "Defined in the baseline" -> the dump itself, not a reconciliation migration replayed after it: the ruling says "present in the schema-baseline dump" (Jakob in prep code-review-2026-10 (2026-10-24)). Such a migration is authored but not applied (schema-baseline, Gap remedy; roadmap header), so the live server may still lack the function. That fallback stays, and deleting it after Jakob applies the migration is follow-up work outside this feature. The criterion reads the dump alone through `RebuildSet.load` with `migrationsDir` set to an empty directory.
  - The dump arrives through schema-baseline, which is blocked on Jakob supplying it (schema-baseline, Blockers). That is this feature's dependency, not a decision left open here, so status stays planned.
  - Failure surface -> a missing RPC reaches the caller as the RPC's own `PostgrestException`, through each method's existing catch-and-rethrow. Every screen already shows its failure SnackBar for any thrown error (checked at HEAD 439b7d5): `groupCreateError` on the group form, `expenseCreateError` in the expense editor, `payBackError` on the record sheet, on settle-up (group_detail_payment.dart) and on friend settle-all (friend_detail_sheet.dart), and `claimLoadError` on the claim screen. Only the group form, the expense editor (no-check half) and the record sheet have failure tests today. Settle-up and friend settle-all share the record sheet's catch-all shape and get no new test. No new copy, no new error type, and never a silent partial write (Jakob in prep code-review-2026-10 (2026-10-24)).
  - Expense SnackBar proof -> at HEAD the editor shows `expenseCreateError` in its catch and then pops in `finally`, and the failure test asserts only the missing check (research/code-review-2026-10.md As-is for editor-failure-keeps-form). If editor-failure-keeps-form has not landed, this feature adds one `expenseCreateError` expectation to that existing test, and asserts nothing about pop or idle, which belong to that plan (editor-failure-keeps-form, first criterion).
  - Claim failure copy -> stays `claimLoadError` ("Couldn't load this expense."), although the failure is a write. The ruling asks for the existing failure path, not new copy (Jakob in prep code-review-2026-10 (2026-10-24)).
  - pay_back fallback -> `_payBackExactMissing`, its memo and the plain `pay_back` branch go, so `payBack` calls only `pay_back_exact` (Jakob in prep code-review-2026-10 (2026-10-24)). The server-side `pay_back` stays, because `pay_back_exact` delegates its insert to it (archived payback-on-behalf, settle-residue). This changes settle-residue's archived Provides, which lists the memoized `pay_back` fallback (research/code-review-2026-10.md, Already settled). `payBackAll` inherits the change through `payBack`, with no change of its own.
  - payback-atomic-recalc -> neither feature depends on the other. If it landed first, this feature reuses its `PaybackRpc` and `payBackRpcOverride`, deletes its `resetPayBackFallback()` together with the memo and its tearDown calls, and replaces its memoized-fallback test (a missing `pay_back_exact` gives the probe plus `pay_back`, then `pay_back` alone) with the third criterion. That is a deliberate contract change, and it changes payback-atomic-recalc's Provides. If this lands first, it adds `PaybackRpc` and `payBackRpcOverride` exactly as payback-atomic-recalc's Provides names them, without the reset, and that plan finds no fallback left to keep.
  - Orphans -> each goes only with the fallback that was its sole user; a kept fallback keeps its helpers. `GroupRepository.resolveMemberWrite` and `GroupMemberWrite` go: their only caller was the group `_saveAllLegacy`, and they are untested (research/code-review-2026-10.md). `stripProvenance` goes, together with the group "the legacy write path strips provenance before PostgREST" in test/model/expense_provenance_test.dart, because its only caller was the expense legacy path. ## Approach
- Start from the dump. This feature cannot begin until schema-baseline has committed supabase/schema/baseline.sql. The first step reads it, records which of `save_group_all`, `save_expense_all`, `pay_back_exact` and `claim_set_unit_shares` it defines, and pins that list in the baseline test, so every deletion rests on a checked fact rather than on the Applied table.
- Then go write by write, one red→green cycle each. Add the seam, write the test that a missing-function error comes back unchanged with nothing else issued, and watch it go red because the fallback runs into the dummy client. Then delete the fallback and its doc-comment promises. Go group save, expense save, payback, then claims only if the dump allows it. The payback step goes after payback-atomic-recalc if that has landed, reusing its seam and retiring its reset and memo test. Otherwise it adds the same seam for that plan to find.
- Finish by deleting what the fallbacks alone used: `resolveMemberWrite` and `GroupMemberWrite`, `stripProvenance` and its tests, the two orphaned key sets, and `isMissingFunctionError` if nothing calls it. The existing widget failure tests, plus the one `expenseCreateError` expectation, prove that each thrown error still ends in the screen's SnackBar.
- Tier: normal — which fallbacks go is decided only once the dump is read, and the payback, expense-save and predicate edits each take a different shape depending on whether payback-atomic-recalc, typed-expense-draft, notification-context-free, helper-split and editor-failure-keeps-form have landed. That leaves real judgment to a planner.
- Likely touchpoints: lib/pages/groups/data/group_repository.dart, lib/pages/expenses/data/expense_repository.dart, lib/pages/expenses/data/expense_conversion.dart, lib/helper/helper.dart (or lib/helper/error_predicates.dart after helper-split), test/model/expense_provenance_test.dart, test/model/write_rpc_no_fallback_test.dart (new), test/supabase/fallback_rpcs_in_baseline_test.dart (new), test/widgets/expense_save_status_test.dart (only if editor-failure-keeps-form has not landed), test/widgets/claim_chips_test.dart (only if the claim fallback goes), and test/pages/groups/payback_atomic_recalc_test.dart (only if payback-atomic-recalc landed first).
- Depends: schema-baseline
- Parallel-with: editor-failure-keeps-form (both may add to the same failure test in expense_save_status_test.dart, an additive rebase), scan-total-applies, group-model-parse-safety, realtime-channel-lifecycle, push-session-lifecycle, housekeeping, presentation-file-split (it keeps claim_chips_test green, and this feature only adds a case), expense-search-escape, guest-merge-rpc and group-write-rpcs (the last three edit other methods of the same repositories, so the rebase is trivial). Not parallel, because they edit the same blocks: payback-atomic-recalc and notification-context-free (`payBack`), typed-expense-draft (the expense `saveAll` fallback branch), helper-split (`isMissingFunctionError`) and injectable-repositories (the static repositories). Whichever lands second rebases.
