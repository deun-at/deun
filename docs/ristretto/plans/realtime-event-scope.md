# realtime-event-scope

## Spec
- Source: idea — code review 2026-10-22 (research/code-review-2026-10.md), finding 8 — the As-is lines tagged "for realtime-event-scope"
- Goal: GroupListNotifier and FriendshipListNotifier subscribe only to changes in the user's own groups and friendships. A realtime refresh of the group list that fails, races another refresh or outlives its notifier never corrupts the list.
- Why: group members using the app · noticed by: a failed save or delete no longer throws away the form, a retried payback no longer double-records, a joining guest no longer rewrites history outside the group

## Contract
- Acceptance:
  - [auto] **Only the user's own rows are asked for.** Every channel that GroupListNotifier and FriendshipListNotifier open carries a filter, and every filter value belongs to the user: a group id from the user's list, or the user's own email (the channel set is ruled under Decisions). With no signed-in email, neither notifier opens any channel. After a rebuild under another account, no channel opened for the previous account is still open, and every new filter carries the new account's email and group ids. Red means the server streams other people's groups and friendships to this device wherever RLS does not stop it.
  - [auto] **Every group of a big user stays live.** For a user in 250 groups, each notifier carries each of those group ids in exactly one `group_update_checker` channel, and no channel carries more than 100 ids (the server's in-filter limit). An update event for any one of the 250 groups refreshes that group's row in the list and reloads the friend list. Red means some of a big user's groups stop updating live.
  - [auto] **Someone else's group never lands in the list.** An insert or update event on a group channel naming a group id outside the user's list starts no fetch and leaves the list exactly as it was.
  - [auto] **New groups appear and go live.** A membership insert or update for the user's email in a group not yet in the list adds that group to the list. That covers a group they created on any device, one they joined, and one another member added them to. A later update event for that group then refreshes its row in the group list and reloads the friend list.
  - [auto] **Deleted groups go and stay gone.** A delete event for one of the user's groups removes it from the list. A fetch for that group that is still in flight when the delete arrives does not bring the group back when it completes. A later checker event for that id adds nothing.
  - [auto] **A group the user was removed from leaves.** When a refresh of a group returns it with no member row for the user (another member hard-removed them), the group leaves the list as a delete would, and later checker events for it add nothing. A soft-removed user keeps the group and its live updates, as a full reload keeps it. Red means a removed user keeps seeing the group, and keeps hearing its updates, until the next full reload.
  - [auto] **The newest read of a group wins.** When a fetch for a group that started earlier completes after one that started later, the list keeps the later fetch's data. The same holds against a full reload (resume or pull-to-refresh). A per-group fetch that started before the reload cannot overwrite the reload's row. A per-group fetch that started after the reload began is not overwritten when the reload completes later.
  - [auto] **A failed refresh changes nothing.** When the per-group fetch throws (no row for `.single()`, no permission, no network), the list keeps exactly the groups and values it had and stays in its data state, so no error is shown. No error escapes the callback, and the next event for that group refreshes it normally.
  - [auto] **Nothing lands after dispose.** GroupListNotifier may be disposed while a per-group fetch or a reload is in flight, and FriendshipListNotifier while its reload is in flight. When that fetch completes, it writes no state and raises no error.
  - [auto] **The friend list follows the user's friendships and groups.** An insert, update or delete event on either friendship channel reloads the friend list after the existing 2 s debounce. So does an event on a friendship group channel, including one for a group that joined the user's list after the friend list was built. A group joining the user's list after the group list's first load also reloads the friend list after the debounce, because the bump of that add or join went out before the group was in the friend list's scope. Red means a friend's balance from a newly joined group (a guest-claiming join brings one along) stays stale until a resume.
  - [auto] **Deletes can reach filtered channels.** A new migration sets replica identity full on `group_update_checker` and `friendship`. It adds `group_member` to the `supabase_realtime` publication only when the table is not already a member, so it can be re-run. Proven by a source-shape test on the migration file. Red means that once the migration is applied, a group another member deleted, or a friend request someone cancelled, still shows on this device, and a group the user is added to never appears live.
  - [auto] A user switch rebuilds both notifiers, which is what moves their filters to the new account. Already enforced by test/provider/auth_switch_invalidation_test.dart ('signedOut invalidates the user-scoped providers (user detail, group list, friendship list) so they refetch' and 'signedIn as a DIFFERENT user invalidates; the same user does not'); must stay green.
  - [auto] `dart format`, `flutter analyze` and `flutter test` pass.
  - [ ] [human] On the live instance with the migration applied, the group list's filtered channels deliver insert, update and delete events, and a group the user is added to appears and goes live without a refresh.
    how: out of reach: the self-hosted realtime server on api.deun.app (`supabase/realtime:v2.34.7`: whether it accepts in-filters with quoted values) and the unapplied migration. - Provides:

  - `const int kRealtimeInFilterMaxValues = 100` and `List<List<String>> chunkForInFilter(Iterable<String> values)`. The function deduplicates and sorts its input, returns chunks of at most 100 values, and returns an empty list for empty input. Both live in lib/helper/realtime_mixin.dart.
  - `RealtimeNotifierMixin.syncInFilterChannels({required Ref ref, required String prefix, required String table, required String column, required Set<String> values, required void Function(PostgresChangePayload) onEvent}): void` keeps one `column=in.(chunk)` channel per `chunkForInFilter` chunk of `values`, named `<prefix>:s<version>:<index>`. A call whose `values` equal (by contents) what the prefix already covers opens and closes nothing; otherwise it closes the prefix's old chunk channels and opens new ones under the next, never-reused version. It lives in lib/helper/realtime_mixin.dart.

- Decisions:
  - Scope -> finding 8 only: the channels of GroupListNotifier and FriendshipListNotifier, their event and reload bodies, one mixin addition and one migration. The channels of ExpenseListNotifier, GroupDetailNotifier and ClaimNotifier stay as they are (research/code-review-2026-10.md As-is; realtime-channel-lifecycle Decisions, Scope).
  - RLS -> not relied on. Scoping comes from realtime filters plus a client-side check, and nothing here reads or changes RLS (Jakob in prep code-review-2026-10 (2026-10-24)). The live state is now known (dump and catalog queries, 2026-10-24/25). group_update_checker and friendship have SELECT policies that already limit insert and update events to the user's own groups and friendships. Deletes are not RLS-filtered. group_member's only policy is `USING (true)`. `supabase_realtime` holds exactly group_update_checker, expense_update_checker and friendship, and every table has default replica identity. The ruling stands for three reasons. Filters are still what lets deletes reach the right subscribers (see Replica identity full). They cut the server's per-subscriber authorization work. group_member, the table this feature adds, has been readable only within the caller's own groups since the 2026-10-25 follow-up migration, so its insert and update events are already scoped by RLS; the filter is still what reaches deletes (rls-hardening Decisions).
  - The user's group ids -> the ids of the groups in GroupListNotifier's list: what `GroupRepository.fetchData("all")` returns, plus groups that events add, minus groups that deletes and removals take away. The groups the user sees are the groups the user hears (planning, from group_list.dart and group_repository.dart).
  - Group channels -> on `group_update_checker`, with a `group_id` in-filter over the user's sorted group ids, at most 100 ids per channel and one channel per chunk. With no group ids there is no group channel. At 110 groups in the whole instance, one chunk is the practical case (rests on unconfirmed domain/supabase-realtime.md: postgres_changes filter limits) (Jakob in prep code-review-2026-10 (2026-10-24); research/code-review-2026-10.md As-is, group-currency-persist count).
  - Re-scope -> runs whenever the set of ids changes, whether through the build result, a reload, a membership event adding a group, or a delete or removal taking one away. The notifier then closes its old chunk channels with `unsubscribeFromChannel` and opens the new ones. A change that leaves the set equal closes and opens nothing, compared by set contents and not by identity, because re-joining a channel drops the events that arrive in the gap. When the set does change, an event for an unchanged group that arrives while the new chunk channels join is missed until the next event or a resume; this is accepted, since the set changes only on an add, a removal or a reload that found a different set. A re-scope never touches the membership or friendship channels (Jakob in prep code-review-2026-10 (2026-10-24): re-scoped on create/join/leave/delete; planning for set equality and the swap gap).
  - Chunk channel names -> carry a scope version, `group_list:s<version>:<index>` and `friendship_group_checker:s<version>:<index>`, so a re-scope never reopens a topic whose leave may still be in flight. realtime_client 2.7.1 `channel()` adds a new channel on every call without deduplicating the topic (pub cache, realtime_client.dart). The version is a notifier field that is never reset, so a rebuild (a user switch) never reuses a name either, because Riverpod keeps one notifier instance across rebuilds (realtime-channel-lifecycle Decisions, `disposeChannels()` at the top of every `build()`). The names stay unique across notifiers.
  - How a new group reaches the list -> through a third channel, `group_list:membership`, on `group_member` filtered `email=eq.<user email>`, reacting to insert and update. `group_update_checker` has no member column (research/code-review-2026-10.md As-is), so a group outside the scope cannot be heard on it, and neither group_detail_edit.dart nor group_join_page.dart touches `groupListProvider`. Through this channel a group the user creates (`save_group_all` inserts their member row and recalculates in one transaction), joins (insert, or `removed_at` cleared) or is added to (`addMember`) appears without a refresh, as it does today. Inserts and updates take the same per-group refresh as a checker event. An `is_favorite` toggle is a membership update too, so it also refreshes that row on each of the user's devices; the optimistic toggle is unchanged. Deletes are excluded, see the replica identity lines (planning, required by Jakob's re-scope-on-create/join ruling).
  - Multi-statement adds -> `addMember` and the join page write the member row before the share recalculation, and the join page also before its guest merge, as separate statements. The membership event can therefore fetch the group before those later statements land, and their closing checker bump arrives before the group is in scope, so neither notifier hears it. The group's row then shows pre-recalculation values until the next event for it, a resume or pull-to-refresh. This is accepted, with no added delay or retry, because group-write-rpcs (`add_group_member`) and guest-merge-rpc (`join_group`) each move the whole write into one transaction, after which the membership event and the final state arrive together (planning, critique; group_repository.dart `addMember`, group_join_page.dart; group-write-rpcs and guest-merge-rpc plans).
  - Insert position -> a group that a refresh adds lands in case-insensitive name order, the sort `onEvent` applies today (planning, from group_list.dart).
  - Leave -> a per-group refresh whose result has no `group_member` row for the user's email (soft-removed rows count as rows) removes the group, as a delete would, and so shrinks the scope. A soft-removed user keeps the group, matching `fetchData`'s summary join. Where RLS hides the group from a removed user, the fetch fails instead, so the failure rule applies and the group stays until the next reload. Users cannot remove themselves (group_members_page.dart shows no action on their own row), so "leave" means another member removed them (Jakob in prep code-review-2026-10 (2026-10-24): re-scoped on leave; planning, from group_repository.dart `removeMember` and `Group.groupSelectString`).
  - Client-side scope check -> GroupListNotifier drops, before any fetch, a checker event whose `group_id` is outside its current scope and a membership event whose email is not the user's. This is defence in depth while in-filter support on the instance is unverified, and it is what makes "someone else's group never lands in the list" testable. FriendshipListNotifier gets no such check, because an extra reload only re-reads the user's own data (planning).
  - Friendship channels -> two of them: `friendship_list:requester` with `requester=eq.<email>` and `friendship_list:addressee` with `addressee=eq.<email>`. Filters combine with AND only, and a friendship row matches on either column (rests on unconfirmed domain/supabase-realtime.md: postgres_changes filter limits) (Jakob in prep code-review-2026-10 (2026-10-24); column names from friendship_repository.dart).
  - Friendship group channels -> reuse the group list's scope. FriendshipListNotifier `ref.listen`s `userGroupIdsProvider` with `fireImmediately` and re-scopes its own chunk channels under the same set-equality rule. It uses `listen`, not `watch`, so a scope change never rebuilds the friend list. An id that enters the scope after the group list's first data schedules the existing debounced reload, because that group's add or join bump went out before the friend list could hear it. The first scope after load and a shrinking scope schedule nothing, since a delete or removal is heard as an in-scope event (Jakob in prep code-review-2026-10 (2026-10-24): "reuses the same group-id scope"; planning, critique for the reload on a scope gain).
  - Ordering -> per group, the read or delete that started last wins. Every per-group fetch, every delete and every full reload takes the next number from one counter when it starts, and a result for a group applies only if no higher-numbered read or delete of that group has applied. A reload drops a group missing from its result unless a read of that group which started later has already applied. This extends Jakob's "latest event wins" to reloads (Jakob in prep code-review-2026-10 (2026-10-24); planning).
  - Failed per-group fetch -> caught. The list is unchanged, the failure goes to `debugPrint` with the group id (the logging `toggleFavorite` already uses), nothing is thrown, and the group's applied number does not move (Jakob in prep code-review-2026-10 (2026-10-24)).
  - Full reload failure -> unchanged from today (`AsyncValue.guard`), since it is not part of finding 8 (planning).
  - Post-await guard -> every await in both notifiers' event and reload paths re-checks `ref.mounted` before writing state. This is the rule realtime-channel-lifecycle set for its own notifiers and left to this feature for these two (realtime-channel-lifecycle Decisions, "GroupListNotifier / FriendshipListNotifier bodies").
  - Opening order -> the membership channel and both friendship channels open at the top of build. The group channels open as soon as the initial fetch has returned ids, since the scope is unknown before then. A bump inside that window is heard only at the next event or the resume reload (planning).
  - No signed-in email -> neither notifier opens a channel, and there is never an unfiltered fallback (planning; dimension b).
  - Replica identity full -> set on `group_update_checker`, because group deletes must reach the filtered group list and GroupDetailNotifier's eq-filtered channel. Also set on `friendship`, because a cancel, decline or remove must reach the other side: a cancelled request left on screen can still be accepted, which upserts a friendship nobody wants (rests on unconfirmed domain/supabase-realtime.md: postgres_changes and DELETE) (Jakob in prep code-review-2026-10 (2026-10-24): "group_update_checker at least").
  - No replica identity full for `group_member` -> its deletes would show every removed member's email to every subscriber, since RLS is not applied to deletes. A hard removal is already heard through the in-scope checker bump that `removeMember` triggers, and that refresh takes the group off the list (see Leave). `expense_update_checker` is left alone too: its subscribers are outside finding 8, and ClaimNotifier's `onEvent` would fetch a deleted expense (rests on unconfirmed domain/supabase-realtime.md: postgres_changes and DELETE) (planning, from group_repository.dart and claim_notifier.dart).
  - Delete exposure -> with replica identity full, a delete carries the whole old row to every subscriber whose filter matches it, whatever RLS says. That is a deleted group's id and timestamp, or a deleted friendship's two emails, status and date. This is accepted for the correctness above. The live state (2026-10-25) makes the trade cheaper than it looked. friendship has RLS, but its PK is `(requester, addressee)`, so with today's default identity every friendship delete already sends both emails to every app's unfiltered `friendship` channel. Once this lands, the new client's filtered channels receive only their own deletes. Older installed builds keep their unfiltered channel and, after the migration, receive the full old row instead of the key: status and created_at on top of what they get today. That lasts until those users update (rests on unconfirmed domain/supabase-realtime.md: postgres_changes and DELETE) (planning; research/code-review-2026-10.md, "Answered by the live instance").

## Approach
- Build on realtime-channel-lifecycle's slot-per-config mixin and its `FakeRealtimeChannelFactory`. First add `unsubscribeFromChannel`, because a re-scope must close chunk channels without touching the membership or friendship channels, and `disposeChannels` closes everything.
- GroupListNotifier then works like this:
  - At the top of build it opens the membership channel and fetches through the `fetchGroups` seam. It computes the scope from the result and opens the chunk channels.
  - Every later write of the list's data goes through one apply-scope step. That step compares id sets and swaps chunk channels only when the sets differ.
  - Checker inserts and updates, and membership inserts and updates, share one per-group refresh: check the scope, take a number, fetch through `fetchGroup`, re-check `ref.mounted` and the number, then write the row in name order, or drop the group when the result has no member row for the user. A delete takes a number and removes the row. A reload takes one number for all the groups it returns.
- `userGroupIdsProvider` maps the list's data to its ids. FriendshipListNotifier listens to it and runs the same swap on its own chunk channels, next to its two side channels and its unchanged 2 s debounce, which a scope gain after the first load also schedules.
- Tests run on `ProviderContainer.test`, with `realtimeChannelFactoryProvider` overridden by the fake. Notifier subclasses override the fetch and email seams with `Completer` futures, and fake_async drives the debounce. A test finds a channel by table and filter in the fake's open log, then fires events on that channel's handle. The migration test reads the SQL file the way test/pages/expenses/expense_rate_migration_test.dart does. The build-overriding fakes in test/widgets/group_list_screen_test.dart and test/pages/friends/friend_list_test.dart open no channels and must keep compiling.
- Tier: normal — the read counter shared by per-group fetches, deletes and reloads, the chunked re-scope with its scope version, and the friend list's reload on a scope gain leave real design choices for a planner.
- Likely touchpoints: lib/helper/realtime_mixin.dart, lib/pages/groups/provider/group_list.dart (and group_list.g.dart via build_runner), lib/pages/friends/provider/friendship_list.dart, supabase/migrations/ (new file), test/helper/realtime_mixin_test.dart, test/provider/group_list_scope_test.dart, test/provider/friendship_list_scope_test.dart, test/pages/groups/realtime_event_scope_migration_test.dart, docs/ristretto/manual-checks.md

## Open findings
- note · supabase/migrations/20261025200000_realtime_event_scope.sql:28-29 (and the header at :5-13) · Both `replica identity full` statements look functionally redundant. Every filtered column is part of a primary key: `group_update_checker` PK is `(group_id)` (baseline.sql:4486), and friendship's is `(requester, addressee)`. Those columns are already in a DELETE's old record under the default identity. Under RLS, the docs say full identity is trimmed back to the primary key anyway. So the "Replica identity full" and "Delete exposure" Decisions rest on a wrong premise (the unconfirmed domain entry), and the header's "receive that full row until they update" overstates the exposure. No user can be harmed: the statements add no data beyond the primary key that deletes already carry, only extra WAL volume. · Fix: it is a Decisions ruling, so take it back to the planner or Jakob to confirm whether to drop the two ALTERs (and what criterion 11 then asserts), and correct the header comment either way.
- note · lib/pages/groups/provider/group_list.dart:233-234 · A membership-event refresh that finishes before the build's first `fetchGroups` returns is dropped (`groups == null`). A group the user is added to in that start-up window does not appear. No user can be harmed beyond the window the "Opening order" ruling already accepts: the group shows at the next event, resume or pull. · Fix: none needed if that ruling is read as covering the membership channel. Otherwise, say so in the plan's Decisions.
