# payback-atomic-recalc

## Spec
- Source: idea — code review 2026-10-22 (research/code-review-2026-10.md), finding 7
- Goal: A payback is written together with its balance recalculation or not at all, so an error never hides a payment that was recorded, and retrying after an error never records it twice.
- Why: group members using the app · noticed by: a failed save or delete no longer throws away the form, a retried payback no longer double-records, a joining guest no longer rewrites history outside the group

## Contract
- Acceptance:
  - [auto] The newest definition of `public.pay_back` in supabase/migrations runs `update_group_member_shares` for the payback's group and the new payback's id after its last insert and before it returns. A payback can then never commit without its balance update, and never outlives a failed one. Red at HEAD, where the newest definition (20260816010000_payback_on_behalf.sql) only inserts.
  - [auto] That newest `pay_back` still rejects, before any insert, a missing payer or payee, a payer equal to the payee, and a payer or payee who is not a current (`removed_at is null`) member of the group. It still stamps the recorder (`auth.uid()`) onto the payback row, still takes `(uuid, text, text, numeric)` and still returns the new id as `uuid`. Red means a payback for a removed member or for oneself records again, a payback recorded on someone's behalf loses its "recorded by" line, or the app's existing call stops matching the function.
  - [auto] The newest definition of `public.pay_back_exact` has no insert of its own and records through `public.pay_back`, so the client's main path gets the same in-transaction recalculation. True today in 20260815020000_settle_residue_exact_payback.sql; red if a later migration re-states it with an insert of its own.
  - [auto] When the payback write succeeds, `GroupRepository.payBack` completes without error after exactly one RPC, `pay_back_exact`. Where `pay_back_exact` is missing, it issues the failed probe plus one `pay_back`, and on later calls `pay_back` alone; this fallback half applies only while the memoized fallback exists (see Decisions, Landing order). It never calls `update_group_member_shares`. Red at HEAD: `payBack` also calls `update_group_member_shares`, and when that fails twice it throws although the payment is recorded.
  - [auto] When the payback write fails with any error other than a missing function, `payBack` throws that error and issues no further RPC, so the same payment is never written a second time. Green at HEAD; red if a retry or a second write comes back.
  - [auto] A failed payback still reaches the user as the generic error, or as the rejection's reason, with the confirm button back to idle so they can try again. A second tap while the write is in flight still writes once, and both RPCs still receive the same four-argument map. Already enforced by test/widgets/record_payback_sheet_test.dart ("an unexpected write failure keeps the generic error", "a rejection from the write says why, not \"could not pay back\"", "a second tap while the write is in flight writes once") and by test/model/group_repository_test.dart (the `GroupRepository.payBackRpcParams` group). These must stay green.
  - [auto] `dart format`, `flutter analyze` and `flutter test` pass.
  - [ ] [human] With the migration applied on api.deun.app, a payback recorded from the app updates `group_shares_summary` in the same transaction as the payback row. Two clients viewing the group both show the balance settled with no further write. A `pay_back` run inside a transaction that is then rolled back leaves neither a payback row nor a change to the summary.

- Decisions:
  - Where the recalculation runs -> inside `pay_back`, after the `expense_entry_share` insert and before `return`, as `perform public.update_group_member_shares(_group_id, new_expense_id)`. These are the same arguments the client passed, so `group_update_checker` and `expense_update_checker` are bumped exactly as before. Precedent: `save_expense_all` / `save_group_all` / `claim_set_unit_shares` already recalculate in the same transaction (research/code-review-2026-10.md; Jakob in prep code-review-2026-10 (2026-10-24)).
  - Why `pay_back` and not a new RPC or `pay_back_exact` -> the payback insert and its guards live only in `pay_back`, and `pay_back_exact` delegates to it, so both entry points inherit the change. `pay_back_exact` is not touched (payback-on-behalf, settle-residue; research/code-review-2026-10.md).
  - Migration body -> the `pay_back` body from 20260816010000_payback_on_behalf.sql copied verbatim (four guard blocks, errcodes, `auth.uid()` attribution, positional `$1..$4`), plus the one `perform`. The signature and `uuid` return stay the same, so `create or replace` replaces the function in place and no overload appears. It stays SECURITY INVOKER with no grant changes, as that file has neither: the recalculation runs with the caller's rights, exactly as the client's separate call did (Jakob in prep code-review-2026-10 (2026-10-24); archived payback-on-behalf).
  - Migration file -> a new timestamped file in supabase/migrations, later than every file present at build time. 20260816010000 and 20260815020000 are applied and stay byte-identical (manual-checks.md, "Never editing an already-applied migration"). This is a build rule, not a criterion.
  - Newest-definition rule -> the source-shape test takes the newest file by filename containing the header `create or replace function public.pay_back(`, so `pay_back_exact`'s own header and its `return public.pay_back(` call never count as a definition. It does the same for the `public.pay_back_exact(` header. Any later re-statement that drops the recalculation or a guard therefore turns it red, including a schema-baseline reconciliation migration with a later timestamp. schema-baseline's own dump lives in supabase/schema/, outside the folder this test reads, and that plan keeps sibling source-shape tests on their own migration files (ruling in prep; schema-baseline plan, Decisions "Reference role").
  - Client -> `payBack` drops its separate `update_group_member_shares` call and the one-shot retry. A thrown error now means nothing was recorded, which is what makes retrying safe (Jakob in prep code-review-2026-10 (2026-10-24)).
  - Old clients -> harmless. They still call `update_group_member_shares` after `pay_back`. The function recalculates from scratch (it is idempotent), so the extra call only bumps the checkers a second time (Jakob in prep code-review-2026-10 (2026-10-24)).
  - No new client fallback -> `pay_back` keeps the same signature, so the client cannot tell whether the recalculation runs server-side, and it does not probe. A client carrying this change against an unmigrated server records paybacks whose balance stays stale until the next write, so Jakob applies the migration before that client reaches users. A push to main already counts, because it deploys the web build. The manual-checks entry says so (roadmap header and manual-checks.md: "check here before shipping"; CLAUDE.md CI/CD).
  - Memoized `pay_back` fallback for a missing `pay_back_exact` -> stays exactly as it is. legacy-fallback-removal removes it later (Jakob in prep code-review-2026-10 (2026-10-24); settle-residue's Provides lists it).
  - Landing order -> no Depends with notification-context-free or legacy-fallback-removal in either direction; all three edit `payBack`, and injectable-repositories depends on this feature. If legacy-fallback-removal landed first, there is no memoized fallback: this feature reuses that plan's `PaybackRpc` / `payBackRpcOverride`, adds no `resetPayBackFallback`, drops the fallback half of the fourth criterion (legacy-fallback-removal's own criterion already pins that a missing `pay_back_exact` throws after one RPC), and only removes the recalculation call and its retry. If notification-context-free landed first, `payBack` takes its `required NotificationSender notifications` instead of a context and `sendNotification`, and the client recalculation sits in the write half of its write/notify split; this feature deletes it there. Its Dart tests then pass a `NotificationSender` over a spy transport instead of a `Builder` context and `sendNotification: false` (legacy-fallback-removal and notification-context-free plans, Decisions).
  - Notifications -> not changed. The payback push still fires only after the payback RPC returns, with the same receivers and copy: through `sendGroupPayBackNotification` at HEAD, or notification-context-free's notify step if that has landed (Jakob in prep code-review-2026-10 (2026-10-24); payback-on-behalf: both-party notification and recorded-by are load-bearing).
  - `payBackAll` -> inherits the change through `payBack`'s write, with no change of its own: one RPC per settled group. Its `Future.wait` can still fail after other groups have committed. A retry re-reads balances, and those are now always current, so it settles only what is still open (research/code-review-2026-10.md As-is: `payBackAll` fans out `payBack` with `sendNotification: false`; after notification-context-free it runs the same write per target and then notifies).

  - (g) test seams -> see "Test seam". `PaybackRecorder` and `FriendSettleAll` are unchanged.

## Approach
- Start red on the server. The source-shape test reads every file in supabase/migrations and takes the newest one containing the `create or replace function public.pay_back(` header. It slices that function's body up to its closing `$function$` and checks three things: `perform public.update_group_member_shares(_group_id, new_expense_id)` sits after the share insert and before `return`; the four guard blocks and `auth.uid()` survive; the signature and return type are unchanged. It applies the same lookup to the `public.pay_back_exact(` header to confirm delegation. The migration then copies 20260816010000's body verbatim and adds the one line. This feature never redefines `update_group_member_shares` or `pay_back_exact`.
- On the client, first route every `supabase.rpc` call in `payBack` through `payBackRpcOverride ?? <default>`, then write the seam tests. They use `testWidgets` with a `Builder` for the context, Supabase initialized with the dummy localhost URL, an explicit `paidBy` and `members` (so there is no roster SELECT) and `sendNotification: false` (or, if notification-context-free landed first, a `NotificationSender` over a spy transport; see Decisions, Landing order). Then delete the try/retry block. `isMissingFunctionError` and `_payBackExactMissing` stay, unless legacy-fallback-removal has already deleted them.
- Sequencing: notification-context-free (the `payBack(context, …)` signature), legacy-fallback-removal (the `pay_back` fallback inside `payBack`) and injectable-repositories (static `GroupRepository`) all edit `payBack` itself, so none runs alongside this feature. injectable-repositories depends on it; with the other two, whichever lands second rebases, as Decisions (Landing order) rules for each order.
- Likely touchpoints: supabase/migrations/ (new file), lib/pages/groups/data/group_repository.dart, test/pages/groups/payback_atomic_recalc_migration_test.dart, test/pages/groups/payback_atomic_recalc_test.dart, docs/ristretto/manual-checks.md
