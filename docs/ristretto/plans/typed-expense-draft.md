# typed-expense-draft

## Spec
- Source: idea — code review 2026-10-22 (research/code-review-2026-10.md), As-is: `ExpenseRepository.saveAll` regex-parses `expense_entry[i][field]` keys; `claimable_form.dart`, `expense_detail.dart` and the `ExpenseSaver` seam build and mirror that map
- Goal: The editor builds one typed `ExpenseDraft` and the repository consumes it, with no string-key parsing left at that boundary, while the save sends exactly what it sends today.
- Why: Jakob as sole maintainer · noticed by: the backend rebuilds from supabase/migrations/, the fallback code paths are gone, the 1500–1900-line files open in pieces

## Contract
- Acceptance:
  - [auto] For the same input, the save sends the same money to the database. A fixed matrix of inputs covers: equal, exact (with one locked member), percentage and shares splits; an exact split whose amounts are all zero; a line that has selected members but no split data; an itemized save with a negative discount line among positive ones; 3000 JPY into a EUR group at 0.0058; and 4.50 CHF at 0.9432 split exact 1.50/1.50/1.50. For each one, the complete `save_expense_all` parameters (the group id, the expense row with its provenance, and every entry row and share row with all of their keys) equal literal expectations captured from today's arithmetic before the switch-over. They are compared on their JSON encoding, so a whole number that turns into a decimal (2 into 2.0), which an integer column can refuse, also fails. Those literals are not edited afterwards. The two converted cases also equal the expected values written in the multi-currency-expense-rate manual check (docs/ristretto/manual-checks.md, steps 3 and 7): entry `amount` 17.40 with `original_amount` 3000; and `fixed_amount` 1.42 for the payer and 1.41 for the other two, summing to the entry's 4.24, with `original_fixed_amount` 1.50 on each row.
  - [auto] Editing an existing expense updates that expense: its id is in the expense row of the payload. Creating one sends no id. Pinned as one edit case and one create case of the same matrix, so a save can never duplicate a record or overwrite another one.
  - [auto] "Add & share for claiming" still turns each itemized line into one claim unit per quantity. A re-save keeps each existing unit's claimers by position: a 3× line re-saved as 4× keeps its three units' claimers and adds one unclaimed unit, and re-saved as 2× keeps the first two units' claimers. A plain multi-quantity line with no split still explodes the same way. Proven end to end: the editor puts each card's existing claims into the draft (widget test through the `ExpenseSaver` seam), and the plan turns them into units (unit test on `planSave`).
  - [auto] The push for a newly created expense goes to the same people with the same amount as today. The receivers are the union of every line's selected members, or every active member for "share for claiming". The amount is the rounded sum of the converted line totals. Editing an expense sends no push. Asserted on the plan's notification part for the matrix cases.
  - [auto] The editor hands over what is on screen. In a widget test through the `ExpenseSaver` seam, an itemized editor with three lines, one removed before saving, hands over exactly the two remaining lines, in on-screen order, each with its typed name, unit price and quantity. A quick-mode save hands over the split mode, per-member split values and locked members that its split section holds.
  - [auto] If the save cannot parse an amount, it still ends in the save-error snackbar with the CTA back to idle, and nothing is written (the saver is never called). It never throws an uncaught exception or leaves a spinner stuck on the button.
  - [auto] Converted saves still convert on the client before the write. Already enforced by test/widgets/expense_editor_currency_rate_test.dart (including "saving that exact split back reproduces its ledger values byte-identically") and test/helper/expense_conversion_test.dart, with the two converted matrix cases above proving the converted values reach the payload. Both files must stay green; the capture in the former reads the draft instead of form keys, and no expected value is edited. test/widgets/expense_editor_rate_prefill_test.dart shares that capture helper but reads only the conversion, so it stays green unchanged.
  - [auto] A reloaded expense still fills each line's amount field with the amount as entered. Already enforced by the `Expense.toJson` cases in test/model/expense_entry_claim_test.dart and test/model/expense_provenance_test.dart; must stay green unchanged.
  - [auto] The save CTA's busy, done and failed behaviour, and the single write per tap, are unchanged. Already enforced by test/widgets/expense_save_status_test.dart; must stay green, with only its `_GatedSave` call signature changed.
  - [auto] The explode math is unchanged. Already enforced by test/model/expense_repository_explode_test.dart; must stay green unchanged.
  - [auto] `dart format`, `flutter analyze` and `flutter test` pass.
- Provides:

  - `ExpenseDraft.markEntriesClaimable({Set<String>? notifyEmails}): ExpenseDraft`. Returns a new draft and leaves the receiver unchanged.
  - `static ExpenseRepository.planSave({required String groupId, String? expenseId, required ExpenseDraft draft, required Currency currency, ExpenseConversion? conversion, String? userId}): ExpenseSavePlan`. Pure, and touches no Supabase.
  - `ExpenseSavePlan { Map<String, dynamic> rpcParams; Set<String> notificationReceivers; double notificationAmount; bool sendsNotification }`. `rpcParams` is the `{_group_id, _expense, _entries}` map for `save_expense_all`. `sendsNotification` is true only on create.
  - `static ExpenseRepository.saveAll`, with only the form-map parameter replaced by `ExpenseDraft draft`. The sender-side parameter stays exactly as it stands at implementation time. Once it has, there is no leading context and that plan's trailing named parameter stays: `saveAll(String groupId, String? expenseId, ExpenseDraft draft, {required Currency currency, ExpenseConversion? conversion, required NotificationSender notifications}): Future<void>`.
  - `typedef ExpenseSaver`: the same shape as `saveAll` above, whichever form that has at implementation time.

- Decisions:
  - Draft shape -> expense-level name, date, payer and category, plus one entry draft per line with name, unit price, quantity, split mode, shares, share data, locked members, claimable flag and existing per-unit claims (Jakob in prep code-review-2026-10 (2026-10-24)). The value classes are hand-written and immutable, with no code generation, like the hand-written `PaybackPlan` value classes (payback-on-behalf).
  - Nullability mirrors what the form can hand over today: expense name, payer and entry name are nullable, and a quick-mode line has no name field, so its entry name stays null. `expenseDate` is non-null because the date field always has an initial value. Tightening any of these would change the payload for those inputs, which the parity ruling rules out (Jakob in prep code-review-2026-10 (2026-10-24)).
  - Split mode is typed as the existing `SplitMode` enum (lib/pages/expenses/data/split_mode.dart). The payload writes `toDbValue()`, which yields the same four strings the form's hidden split-mode field holds today, and a missing field defaults to equal, as today (parity ruling, same source).
  - Number types are carried, not converted -> `shareData` keeps each value's runtime type as the split section produced it, so shares-mode parts stay `int`, and `quantity`, `sort_id` and `item_group_seq` stay `int` in the payload. Dart's `==` treats 2 and 2.0 as equal, so criterion 1 compares JSON encodings; `save_expense_all` loads these rows through `jsonb_populate_record` into integer columns (supabase/migrations/20260816020000_expense_entry_currency_rate.sql). Parity ruling, same source.
  - Parity is the contract (Jakob in prep code-review-2026-10 (2026-10-24)) -> for the same user input, the `save_expense_all` parameters and the notification receivers and amount are identical to today's. That includes the key set of each share row (the no-split-data fallback rows carry only email and percentage), the all-zero-exact fallback to equal, and the implicit claimable rule (quantity above 1, no shares, no split data). The implicit rule is unreachable from the editor today, because the Itemized CTA always saves through the claimable path and Quick registers no quantity field; it stays in `planSave` because that is the repository's contract. Existing claims are still added only on the claimable path. Pre-existing quirks are kept, not fixed; a fix is a separate feature.
  - Characterize before switching -> Unit 1 captures the expected payload literals from the unchanged arithmetic, and no later unit edits them. This is the discipline multi-currency-expense-rate used ("every existing money-math test passes without its expected values being edited").
  - Pure plan seam -> `planSave` holds all payload and notification arithmetic. `saveAll` shrinks to: plan, call the RPC with `plan.rpcParams`, the existing legacy fallback while it exists, then notify from the plan. Precedent: `GroupRepository.planPayBack` / `payBackRpcParams` (payback-on-behalf). This makes the converted exact-split apportionment reachable by a unit test; multi-currency-expense-rate could verify it only by a manual SQL check, because no test executes `saveAll` (roadmap row, multi-currency-expense-rate).
  - `ExpenseSaver` takes the draft (the brief left this to the plan, Jakob in prep code-review-2026-10 (2026-10-24)) -> the typedef mirrors the new `saveAll`, so production still passes the repository method itself, and the tests capture typed values instead of reading `expense_entry[0][...]` keys.
  - BuildContext -> no dependency on notification-context-free in either direction. If it has landed, `saveAll` and `ExpenseSaver` take its trailing `required NotificationSender notifications` named parameter and no context, and this feature leaves that parameter as it is; if not, they keep exactly today's leading context. A context is never re-added (Jakob in prep code-review-2026-10 (2026-10-24); notification-context-free plan, Decisions). `userId` is a `planSave` parameter, and `saveAll` passes the signed-in user's id, as today. If injectable-repositories has landed first, `saveAll` is an `ExpenseRepository` instance method that passes its `CurrentUser`'s id, and `planSave` stays static and pure (injectable-repositories plan, Decisions "Pure statics").
  - Legacy fallback -> no dependency on legacy-fallback-removal in either direction. If it has landed first, `saveAll` has no `isMissingFunctionError` branch, so it shrinks to plan, call `save_expense_all` with `plan.rpcParams` (through that plan's `saveExpenseAllOverride` seam, which keeps taking the params map), then notify from the plan. If not, the legacy branch stays and receives the planned maps (legacy-fallback-removal plan, Decisions "Signatures").
  - Seam closures added by plans that land first -> every test that injects an `ExpenseSaver` moves to the draft-taking signature in the switch-over unit, with no expected value edited and no assertion removed: besides the two suites named in Acceptance, that is test/widgets/expense_editor_rescan_test.dart if scan-total-applies has landed (its save criteria then read the draft, as that plan anticipates) and the saver injected in test/widgets/expense_editor_delete_guard_test.dart if editor-failure-keeps-form has landed (scan-total-applies and editor-failure-keeps-form plans, Decisions on tests).
  - No string-key parsing at the repository boundary (Jakob in prep code-review-2026-10 (2026-10-24)) -> `saveAll` and `planSave` take no `Map<String, dynamic>` of form values. ## Approach
- Characterize first, then swap the input type underneath fixed expectations. Unit 1 is a pure extract-function refactor: today's arithmetic moves verbatim into `planSave`, still over the form map, and the matrix literals are captured from it. Only then does the input change to the draft. The literals not changing is the proof that the payload is identical, so the order of the units matters.
- `planSave` builds the expense row, the entry and share rows (including the explode for claimable lines) and the notification receivers and amount, in one pass over `draft.entries`. Sort ids follow list order, which the editor now makes explicit as on-screen order, where today it was implicit in the FormBuilder value map's registration order (the same order, because the form clears an unregistered field's value). `saveAll` keeps the RPC call, the `isMissingFunctionError` legacy branch (unless legacy-fallback-removal has already deleted it) and the create-only notification.
- In the editor, `_saveExpense` replaces the map plumbing with a private draft builder over `_entries`. In quick mode, the amount comes from the expense-level field (same registered name) and the split fields from the entry widget. Itemized cards register only name, amount and quantity, so their split fields take the defaults. On the claimable path (the Itemized CTA) the editor calls `draft.markEntriesClaimable(notifyEmails: active member emails)` and fills each line's `existingClaims` from the card's `unitClaims`. expense_entry_widget.dart needs no change: its field names stay.
- Same files as other code-review-2026-10 features, with no dependency on any of them. notification-context-free (the `saveAll` signature), legacy-fallback-removal (the fallback branch), editor-failure-keeps-form (`_saveExpense`), expense-editor-split, scan-total-applies, injectable-repositories, helper-split, expense-search-escape and group-write-rpcs (`ExpenseRepository.delete` only) all touch these files. presentation-file-split shares no code file with this feature and may run alongside it (its Parallel-with): this feature leaves expense_entry_widget.dart untouched and relies only on the field names that plan keeps byte-identical, and that plan takes the suites this feature rewrites as this feature leaves them. Whichever lands second rebases.
- Tier: normal — the characterization matrix, the editor's draft builder across Quick and Itemized, and the rebase against several same-file features leave real choices for a planner.
