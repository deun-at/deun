# guest-merge-rpc

## Spec
- Source: idea — code review 2026-10-22 (research/code-review-2026-10.md), finding 6 (guest merge in `group_join_page.dart`; first raised as docs/CODE_REVIEW_2026-07-07.md §1.1)
- Goal: An invite-link join, including claiming a guest placeholder, either happens completely and only inside the joined group, or does not happen at all.
- Why: group members using the app · noticed by: a failed save or delete no longer throws away the form, a retried payback no longer double-records, a joining guest no longer rewrites history outside the group

- Decisions:
  - Member-write lock -> `join_group` takes the SAME transaction-scoped, per-group advisory lock as group-write-rpcs' `add_group_member` / `remove_group_member`, as its first statement, so a join and an add of the same email can never interleave (Jakob in prep code-review-2026-10 (2026-10-25)). One key definition, not two copies: the lock is taken through a single SQL helper, `public.lock_group_member_writes(_group_id uuid)` (advisory xact lock on a key derived from the group id). Whichever of guest-merge-rpc and group-write-rpcs lands first creates it with `create or replace`, and the other reuses it unchanged. Neither plan depends on the other.
  - Transaction boundary -> the whole join is one RPC transaction: the membership insert or `removed_at` clear, the optional guest merge and the recalc. Jakob in prep code-review-2026-10 (2026-10-24); the advice comes from docs/CODE_REVIEW_2026-07-07.md §1.1 via research/code-review-2026-10.md.
  - Merge scope -> `paid_by` is rewritten only on that group's expenses, and shares only on entries of that group's expenses. The guest's `group_member` row is removed for that group only. Jakob in prep code-review-2026-10 (2026-10-24); research/code-review-2026-10.md (cross-group damage needs one guest in two groups).
  - Guest `user` row -> deleted only when the guest has no `group_member` rows left anywhere (Jakob in prep code-review-2026-10 (2026-10-24), after CODE_REVIEW_2026-07-07 §1.1). The live dump (2026-10-24) changes how that has to be guarded, because every FK to `user(email)` is `ON DELETE CASCADE`: `expense.paid_by`, `expense_entry_share.email`, `group_member.email`, `group_shares_summary.paid_by`/`paid_for` and `friendship`. A delete never fails on a leftover reference. Instead it silently deletes that reference, and RI actions bypass RLS. So:
    - There is no `exception when foreign_key_violation` block, because it would be dead code.
    - The check also covers `expense_entry_share` and `group_shares_summary`, and it runs after the recalc so this group's own summary rows are already rebuilt.
    - Visibility under SECURITY INVOKER: since the 2026-10-25 RLS stopgap and its follow-up (both applied), the joiner sees memberships, shares and summary rows only of groups they belong to, so an invoker-side `exists` would miss the guest's other groups. The check therefore calls `public.has_any_membership()`, which sees every membership. Memberships alone are enough: a guest with an expense, share or summary row in a group always has a group_member row there, because a soft removal keeps the row and a hard removal requires no history.
    - A leftover reference keeps the row, which is harmless because guests are excluded from search (research/code-review-2026-10.md, user_repository.dart), and the join is not rolled back for it.
  - Today's damage is worse than "rewrites outside the group": group_join_page.dart rewrites shares in every group (shares have no RLS), then deletes the guest `user` row unconditionally. That cascade-deletes a two-group guest's expenses and memberships in the other group (research/code-review-2026-10.md, "Answered by the live instance").
  - Statement order -> the recalc runs before the guest `user` delete. `group_shares_summary.paid_by`/`paid_for` embed the `user` table (`Group.groupSelectString` in lib/pages/groups/data/group_model.dart), and `update_group_member_shares` deletes and rebuilds the group's summary rows (supabase/migrations/20260815010000_group_member_removal.sql). So no summary row of this group may still name the guest when its `user` row goes.
  - Guest validation -> the RPC refuses, with no write, unless `_guest_email` has an active (`removed_at is null`) `group_member` row in `_group_id` and a `user` row with `is_guest` true. Jakob in prep code-review-2026-10 (2026-10-24). "Member" means current member, matching `pay_back`'s current-member guard (payback-on-behalf) and group-member-removal's rule that pickers bind to active members. So the picker drops soft-removed guests as well.
  - Joiner identity -> `join_group` takes no joiner parameter. The joiner is `auth.jwt() ->> 'email'`, the same account email as the `supabase.auth.currentUser.email` that group_join_page.dart uses today. A null email raises. Identity stays the email (dimension b).
  - Membership write -> no row means insert (`group_id`, `email`, `is_favorite` false, the columns `addMember` writes). A soft-removed row means clearing `removed_at`. An active row means no membership write. The merge is decided independently of all three: this carries over group-member-removal's round-3 rule (research/code-review-2026-10.md, "already settled"), now pinned by the migration shape test.
  - Silent RLS no-ops -> under RLS, an UPDATE/DELETE that a policy filters out affects zero rows without raising (research/code-review-2026-10.md, Open). So the RPC checks row counts after the `removed_at` clear and after the guest membership delete, and checks that no guest rows remain in the group. Any failure raises. The residual check only sees rows the joiner may SELECT, so a row hidden from SELECT and UPDATE alike slips past it; the second manual check covers that. The same check catches two joiners claiming one guest at once: the second one rolls back.
  - Security mode -> SECURITY INVOKER, like every sibling RPC (Jakob in prep code-review-2026-10 (2026-10-24)). The client already performs these writes under RLS today, so privileges are unchanged. The live policies (dump 2026-10-24) allow every write. group_member and user are open (`USING (true)`). Expense UPDATE requires the caller to be a member of the expense's group, which holds once the join's own insert or `removed_at` clear has run. No policy checks `removed_at`. Shares and summary have no RLS, and `update_group_member_shares` writes only checker rows (membership-gated) and summary rows. So the second [human] criterion is expected to pass and is kept as the live confirmation. If it fails anyway, Jakob decides on SECURITY DEFINER with an explicit membership check, as a follow-up. rls-hardening tightens these policies later, and its plan keeps `join_group` working.

## Approach
- Strategy: replace the page's client writes (membership insert or `removed_at` clear, four merge writes, recalc) with one call to a new `join_group` RPC. Its body runs in this order:
  - resolve the joiner from the session;
  - check the named guest, raising on any refusal before any write;
  - insert the joiner's membership, or clear its `removed_at` (raising if no row changed), or leave an active row alone;
  - when a guest is named, rewrite `paid_by` on that group's expenses and share emails on that group's entries, delete the guest's membership in that group, and raise if the delete removed nothing or guest rows remain;
  - run `update_group_member_shares` for the group with no expense id, as `save_group_all` does;
  - delete the guest `user` row only when no membership, share or summary row names the guest any more (the FKs cascade, so a delete must never run while a reference remains).
- Write the migration first, with its shape test asserting each of those properties against the file text. Assert refusals and predicates, not formatting, so a reformat stays green and a dropped guard goes red.
- Then build the repository surface. `joinGroupRpcName` and `joinGroupRpcParams` are the one name and argument map, cross-checked against the migration. `fetchJoinState` reads the roster through `_groupRoster`'s select plus the session email and hands it to the pure `resolveGroupJoinState`.
- Finally move the page onto the three seams. `_checkAlreadyMember` and `_fetchGuestMembers` become one `loadJoinState` call. `_joinGroup` becomes `joinGroup(groupId, guestEmail: _selectedGuestEmail)` followed by `loadGroup` and the existing `go('/group/details')`. The catch, the SnackBar and the `_joining` guard stay as they are. The guest tiles render `GroupMember` models rather than raw maps.
- Overlap: group-write-rpcs also edits group_repository.dart, member_removal.dart, member_add.dart (it deletes `resolveMemberAdd`, whose doc comment names `resolveGroupJoin`) and test/model/group_repository_test.dart, in other members. Whichever lands second rebases.
