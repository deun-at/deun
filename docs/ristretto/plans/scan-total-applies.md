# scan-total-applies

## Spec
- Source: idea — code review 2026-10-22 (research/code-review-2026-10.md), As-is: `_scanReceipt` total-only branch (lib/pages/expenses/presentation/expense_detail.dart 1103-1108) and the missing scan seam (test/widgets/expense_itemized_editor_test.dart note)
- Goal: A receipt rescanned inside the editor that yields only a total puts that total into the first item's amount, where it is shown and saved, instead of silently leaving the old amount in place.
- Why: group members using the app · noticed by: a failed save or delete no longer throws away the form, a retried payback no longer double-records, a joining guest no longer rewrites history outside the group

## Contract
- Acceptance:
  - [auto] In the Itemized layout with one item that has no amount yet, a rescan that returns only a total of 42.80 shows 42.80 as that item's unit price, as its line total and as the itemized total, and the saved expense carries 42.80 as that item's amount.
  - [auto] When the first item already holds an amount the user entered, a total-only rescan replaces it in the item row, in the itemized total and in the save. This also holds when an earlier scan had put that same total there before the user changed it.
  - [auto] The total is written at the entry currency's precision, never the group's: on an expense entered in CHF inside a JPY group, a scanned 12.34 shows as 12.34 and is saved as an entered amount of 12.34 CHF, not 12.
  - [auto] With every item removed, a total-only rescan leaves exactly one item holding the total, and the save carries it.
  - [auto] With two or more items, a total-only rescan changes only the first item's amount. Every other item is saved with its name and amount unchanged.
  - [auto] After a total-only rescan, leaving the editor without saving raises the discard confirmation instead of closing the editor.
  - [auto] A total-only rescan that carries a merchant name and a date still applies both: the save carries the scanned name and date.
  - [auto] A rescan returning line items replaces the current items with exactly the scanned lines. The save carries one entry per scanned line with its scanned name and amount, and none of the items that were there before.
  - [auto] In the editor as the app opens it, tapping Scan in the Itemized header still opens the receipt scanner.
  - [auto] The behaviour around the rescan does not change. Already enforced by, and must stay green: "itemized item card: editing unit price updates the line total" in test/widgets/expense_entry_widget_test.dart (the row's own keypad); "itemized total updates live when an item quantity changes" and "Quick toggle is honored even with multiple items (collapses)" in test/widgets/expense_itemized_editor_test.dart; "switching back re-renders the item row, not just the header and the save" in test/widgets/expense_editor_currency_rate_test.dart (the row adopting a re-seeded amount); the `ReceiptItemsPreview` and `ReceiptScannerSheet` groups in test/widgets/receipt_scanner_sheet_test.dart; "tapping Scan opens the receipt scanner; Add expense is wired" in test/pages/groups/v3_header_migration_test.dart (the scan before the editor opens); and test/widgets/expense_save_status_test.dart (the save CTA cycle).
  - [auto] `dart format`, `flutter analyze` and `flutter test` pass.

## Approach
- Tier: normal — the route by which the Itemized row adopts an amount written from outside is left to the planner, and the same-total case needs a two-scan test with the row keypad used in between.
- Strategy: seam first, because no failing rescan test can be written without it; `_scanReceipt` awaits `widget.scanReceipt` and falls back to today's sheet when it is null. Then the total-only branch: compute the text once in the entry currency, find the first item's amount field by name through `_formKey`, and write it in the order `_openAmountKeypad` uses (state first, then `field.didChange`). The trap is the Itemized row: it draws price and line total from `_unitPrice` and only adopts a parent change through a changed `initialAmount`, which misses the same-total case. The smallest fix is for the row's unit-price field (`_buildUnitPriceField`) to adopt a value changed from outside, through an `onChanged` that parses it, compares it with `_unitPrice` and runs `_onTotalChanged`; the update inside `_openUnitPriceKeypad` then becomes a harmless duplicate. Another route is fine as long as the same-total criterion holds. Move `_itemizedOverride = true` into the line-items branch. For zero items, add an entry seeded with the text, the way the line-item branch adds its entries. To test: dismiss the auto-opened keypad (as `_pump` in test/widgets/expense_itemized_editor_test.dart does), switch to Itemized, tap Scan, let the seam return a fixed `ReceiptScanResult`, save with the itemized CTA, and read the captured payload.
- Likely touchpoints: lib/pages/expenses/presentation/expense_detail.dart (constructor seams, `_scanReceipt`, `_openAmountKeypad` as the channel reference), lib/pages/expenses/presentation/expense_entry_widget.dart (`_buildUnitPriceField`, `didUpdateWidget`, `_openUnitPriceKeypad`), test/widgets/expense_editor_rescan_test.dart (new)
- Depends: —
- Parallel-with: payback-atomic-recalc, guest-merge-rpc, expense-search-escape, group-model-parse-safety, group-write-rpcs, realtime-channel-lifecycle, push-session-lifecycle, schema-baseline, housekeeping (disjoint files)
- Not parallel, because they edit the same files or seams: editor-failure-keeps-form, typed-expense-draft and notification-context-free (expense_detail.dart, and the `ExpenseSaver` shape the new test's capturing closure implements), expense-editor-split (splits expense_detail.dart), presentation-file-split (splits expense_entry_widget.dart)
