# group-write-rpcs — Member add/remove, group delete and expense delete each commit as one transaction

## Spec
- Source: idea — code review 2026-10-22 (research/code-review-2026-10.md), architecture item `member-write-rpcs` (renamed and widened to expense delete by Jakob) + the Open item on `ExpenseRepository.delete`'s three-statement shape
- Flight: atomic-writes
- Goal: The four multi-statement group writes the client runs today (add member, remove member, delete group, delete expense) each commit as one server transaction, recalc and realtime cleanup included, or not at all.
- Why: group members using the app · noticed by: an add, removal or delete that fails half-way leaves nothing half-done (no removed member whose balances were never recalculated, no deleted expense still counted, no deleted group lingering in another member's list), and a removal can no longer slip through on a balance or history that changed in the same instant

## Contract
- Acceptance:
  - [auto] Removing a member who is not settled in the group's own currency writes nothing and answers `blocked` with the magnitude. This applies whether they owe or are owed: unsettled means the absolute value of their `group_shares_summary.total_share_amount` (`paid_for` = their email, 0 when there is no row) is at or above the epsilon the client sent. Proven by a source-shape test on the new migration. `remove_group_member` compares `abs(` of that balance to `_settled_epsilon` with `>=`, the exact mirror of `isSettled`'s strict `<`, and its blocked `return` comes before its first `group_member` write.
  - [auto] A settled member who paid for any of the group's expenses, or holds a share on any of its entries, is soft-removed: `removed_at` is stamped and the row is kept. Only a settled member with neither is hard-deleted. Proven by a source-shape test: the history check covers both `expense.paid_by = _email` and an `expense_entry_share.email = _email` reached through `expense_entry` to an expense of `_group_id`. The soft branch only updates `removed_at`, and only the hard branch deletes. If this goes red, a payer with no share of their own gets hard-deleted and the debts owed to them disappear from every balance.
  - [auto] A removal cannot slip through against another write landing in the same instant. Two member writes on one group never interleave, and an expense, payback or claim being saved anywhere is either fully visible to the removal's balance and history reads or waits until the removal commits. Proven by a source-shape test: `add_group_member` and `remove_group_member` each take the group's advisory lock as their first statement, and `remove_group_member` takes the `share`-mode locks on `public.expense` and `public.expense_entry_share` (see Decisions, Serialization) before its first read. If this goes red, a member is hard-removed while an expense naming them is being saved, and that expense's debts drop out of every balance.
  - [auto] `GroupRepository.removeMember` sends the settled epsilon of the group's own currency: 0.005 for a EUR group and 0.5 for a JPY group. Proven by a unit test on the pure `removeMemberRpcParams`. If this goes red, a member left with a ¥0.30 rounding remainder can never be removed, or a member still owed €0.30 is removed.
  - [auto] Each server answer maps to exactly the outcome the Members page already acts on, and any other answer throws instead of reporting a success. Add answers: `'inserted'` → `MemberAddOutcome.inserted`, `'re_added'` → `reAdded`, `'already_member'` → `alreadyMember`. Remove answers: `{outcome: 'blocked', outstanding: 12.5}` → `MemberRemovalBlocked(outstanding: 12.5)`, `'soft_removed'` → `MemberRemovalSoftRemoved`, `'hard_removed'` → `MemberRemovalHardRemoved`. Proven by unit tests on `memberAddOutcomeFromRpc` and `memberRemovalOutcomeFromRpc`. If this goes red, a member who was already in the group gets a "you were added" push and no "already in the group" notice, or a garbled answer passes silently instead of showing the error snackbar.
  - [auto] Adding someone with a soft-removed row clears `removed_at` and inserts no second row. Adding an active member writes nothing. Anyone else gets exactly one new row with `is_favorite` false. Proven by a source-shape test on `add_group_member`. If this goes red, a returning member is duplicated, or their history counts twice.
  - [auto] Every add or removal that answers `inserted`, `re_added`, `soft_removed` or `hard_removed` runs `update_group_member_shares(_group_id, null)` inside the same function, after its write. That recalculates balances and bumps `group_update_checker`, so other clients' open group detail follows the change. Proven by a source-shape test. If this goes red, balances keep counting the old roster, or another member's open group never shows the change.
  - [auto] Deleting an expense removes that expense, removes its `expense_update_checker` row, and recalculates the group's shares, all in one function. The recalc passes a null expense id, so the deleted row is never re-announced to other ledgers. Proven by a source-shape test on `delete_expense`. If this goes red, balances keep counting a deleted expense, or other clients' ledgers try to fetch a row that no longer exists.
  - [auto] Deleting a group removes the `group` row and its `group_update_checker` row in one function and never calls `update_group_member_shares`, which would re-create the checker row. Proven by a source-shape test on `delete_group`. If this goes red, other members keep a dead group in their list.
  - [auto] The argument names each Dart call sends are exactly the parameters its SQL function declares, in order, for all four RPCs. Proven by a test that reads the migration and compares it with `addMemberRpcParams`, `removeMemberRpcParams`, `GroupRepository.deleteRpcParams` and `ExpenseRepository.deleteRpcParams`. If this goes red, every add, remove or delete fails on the live instance.
  - [auto] Nobody can do through the four RPCs what RLS forbids them today: none of the four is `security definer`, so each runs as the caller, exactly like the direct statements it replaces. Proven by a source-shape test.
  - [auto] What the user sees around these writes does not change. This is already enforced, and must stay green with no edits, by:
    - test/pages/groups/group_member_add_flow_test.dart: "adding someone already in the group says so and adds no second row", "a failed add leaves the group attributes untouched and the query in the field", "a settled removal goes through GroupRepository.removeMember, never a direct delete", "a hard removal commits with no dialog", "a soft removal confirms once and says the past expenses stay", "cancelling the soft-removal confirmation writes nothing" and "a failed guest creation says so and keeps the name for a retry".
    - test/widgets/payback_detail_sheet_test.dart: "confirming hard-deletes the payback row through the shared expense delete", "a payback recorded on someone else behalf deletes by the same path" and "a failed delete keeps the sheet open and says so".
    - test/model/member_removal_test.dart: the `resolveMemberRemoval` group (the preview's epsilon boundary, 0.004 settled and 0.005 blocked in both signs).
  - [auto] `dart format`, `flutter analyze` and `flutter test` pass.
  - [human] With the migration applied on the live instance, adding and removing behave as specified. Add: a new member is inserted, a soft-removed member is re-added and an active member writes nothing. Remove: an unsettled member is blocked with no row change; a settled member with history gets `removed_at` stamped while their shares and every member's balance stay identical; a settled member without history loses their row. A second client's open group detail follows each change.
  - [human] With the migration applied, deleting an expense, and separately a payback row, puts every member's balance back to exactly its value before that row existed. `group_shares_summary` keeps no leftover row, and the row leaves a second client's open ledger.
  - [human] With the migration applied, deleting a group takes it off a second member's group list, and its `group_update_checker` row is gone.

- Decisions:
  - Scope: four writes, each one RPC transaction that includes the recalc and checker cleanup it performs today: `addMember`, `removeMember`, `GroupRepository.delete` and `ExpenseRepository.delete`. `member-write-rpcs` is renamed `group-write-rpcs` and takes in expense delete. (Jakob in prep code-review-2026-10 (2026-10-24); research/code-review-2026-10.md As-is lines for member-write-rpcs, and the Open item on `ExpenseRepository.delete`.)
  - Where the removal is decided: inside `remove_group_member`. The balance comes from `group_shares_summary` and history is `paid_by` on the group's expenses or a share on their entries, so the removal semantics (block while unsettled, soft-remove with history, hard-remove without, ledger math never changes) hold without a client round trip between decision and write, and, with the locks under Serialization, with no race. The balance is read from one of the member's `group_shares_summary` rows (`paid_for` = `_email`), never summed: `total_share_amount` repeats identically on each of their rows, exactly as `_memberGroupBalance` reads it today. (Jakob in prep code-review-2026-10 (2026-10-24); archived group-member-removal; group_repository.dart `_memberGroupBalance`.)
  - Settled threshold: the client sends `group.currency.settledEpsilon` as `_settled_epsilon`, and the server blocks iff the absolute balance is at or above it, the mirror of `isSettled`. The server gets no epsilon constant of its own. (Jakob in prep code-review-2026-10 (2026-10-24); archived settle-residue.)
  - Preview: stays client-side and unchanged (`previewMemberRemoval`, `resolveMemberRemoval`, `_memberGroupBalance`, `_hasExpenseHistory`). `removeMember` no longer calls the preview and never passes an outcome to the server; the server re-resolves. (Jakob in prep code-review-2026-10 (2026-10-24); archived group-member-add-flow, "preview before write".)
  - Where the add is decided: inside `add_group_member`, which returns the outcome. `resolveMemberAdd` loses its only caller, so it is deleted together with its `resolveMemberAdd` test group in test/model/member_add_test.dart. The `MemberAddOutcome` enum stays as the return type. `shouldNotifyAddedMember` and `addCandidateExclusions` are unchanged in behaviour; the doc comment on `addCandidateExclusions` that names `[resolveMemberAdd]` is repointed at `add_group_member`, so no doc reference dangles. (Jakob in prep code-review-2026-10 (2026-10-24); technical ruling in prep: one resolver, not two that can drift.)
  - Answer shapes: add returns text, remove returns jsonb, the two deletes return void. An unrecognised answer throws a `FormatException`, which the existing catch blocks turn into the existing error snackbar. (Ruling in prep.)
  - Shared member-write lock -> guest-merge-rpc's `join_group` takes the same per-group advisory lock (Jakob in prep code-review-2026-10 (2026-10-25)). The lock is taken through one SQL helper, `public.lock_group_member_writes(_group_id uuid)`, that `add_group_member` and `remove_group_member` call as their first statement. Whichever of the two plans lands first creates it with `create or replace`, and the other reuses it unchanged. Neither plan depends on the other.
  - Serialization: Jakob's ruling is that the removal semantics hold with no race, and a decision taken inside a READ COMMITTED transaction does not achieve that alone. So, first, `add_group_member` and `remove_group_member` take a transaction-scoped advisory lock keyed on the group id, so two member writes on one group never interleave (no double insert, no remove racing a re-add). An advisory lock rather than `for update` on `group`, because a row lock would depend on unseen UPDATE policies. Second, `remove_group_member`, after the advisory lock and before its first read, locks `public.expense` and `public.expense_entry_share` in `share` mode. Every writer that can create history or move a balance takes `row exclusive` on one of them: `save_expense_all`, `pay_back`, `claim_set_unit_shares`, the guest merge and the client's expense delete. An in-flight writer therefore commits before the removal reads, and a new one waits until the removal commits. The functions stay volatile (the plpgsql default), so each statement after the lock reads a fresh snapshot. The removal itself writes neither table, so its lock never has to upgrade. This closes the window without re-creating those applied RPCs, which would also collide with payback-atomic-recalc's `pay_back`. The cost is accepted: expense writes in every group pause for the milliseconds a removal holds the lock, and removals are rare. `add_group_member` takes no table lock, because an add decides nothing from expenses. Table locks need table-level privileges, not RLS policies. The live dump (2026-10-24) shows `GRANT ALL` on `expense` and `expense_entry_share` to `authenticated`, so the `share` locks are permitted. The removal walk in Manual-Checks still confirms it. `group_member` has PK `(email, group_id)`, so a double insert was never possible as a duplicate row; the advisory lock turns that race into serialized success instead of a 23505 error, and it still keeps a remove from racing a re-add. (Jakob in prep code-review-2026-10 (2026-10-24), "hold with no race"; the lock mechanism is a technical ruling in critique; research/code-review-2026-10.md, "Answered by the live instance".)
  - Parity with today: a blocked removal and an already-member add write nothing and do not recalculate. Every other branch recalculates even when its statement matched no row, as today. A removal whose target has no row is decided exactly as today (balance 0, so it is a hard remove of nothing, or a soft remove if they hold history). Two deliberate differences: soft-remove stamps only an active row (`removed_at is null`), so a repeated removal keeps the first timestamp; and expense delete is scoped to the group (see Expense delete). (Ruling in prep; archived group-member-removal: `removed_at` is the auditable event.)
  - Expense delete: deletes `where id = _expense_id and group_id = _group_id`, so a mismatched pair writes nothing instead of recalculating the wrong group. It deletes that expense's `expense_update_checker` row (the DELETE event `ExpenseListNotifier` drops the row on) and recalculates with a null expense id. Payback rows go through the same function with no special case. (Ruling in prep; archived payback-row-delete.)
  - Group delete: deletes the `group` row, then its `group_update_checker` row (the DELETE event `GroupListNotifier` drops the group on), and never recalculates. Neither delete adds child-row statements: the RPC runs today's statements, and whatever the live schema cascades stays its business. The live dump (2026-10-24) shows what that is. Deleting a `group` cascades its expenses (then entries and shares), members, summary rows, reminders and both checker tables. Deleting an `expense` cascades its entries, shares and `expense_update_checker` row. Neither checker table has a DELETE policy, so the explicit checker deletes, today's and the RPC's, are RLS no-ops. The cascade is what removes the row, and its DELETE event still reaches realtime because RI actions bypass RLS. The explicit statements stay as written: they are harmless, they keep the criteria's source shape, and they take effect if rls-hardening adds a DELETE policy. (Ruling in prep; research/code-review-2026-10.md, "Answered by the live instance".)
  - Security: all four functions are SECURITY INVOKER (implicit, like `save_group_all` and `pay_back`) and carry no GRANT statements (no migration has any), so RLS decides exactly as it does for today's direct statements. (Jakob in prep code-review-2026-10 (2026-10-24).)
  - (a) Currency: only removal touches money, and it does so through the epsilon above; `outstanding` is in the group's currency. Provenance columns: not applicable, since the rows are deleted whole, as today.
  - (b) Identity: `_email` is matched against `group_member.email`, `expense.paid_by` and `expense_entry_share.email`.
  - (c) Soft-removed members: these RPCs are now the only writers of `removed_at` from the members flow (stamp on soft-remove, clear on re-add). `activeMembers` and `groupMembers` are unchanged.
  - (d) Guests: a `guest+…@guest.invalid` member is added and removed by the same RPCs with no special case. Guest creation stays `UserRepository.createGuest` before `addMember`. Removal never deletes a `user` row; guest-merge-rpc owns guest rows.
  - (e) Locale: no new user-facing strings. The existing `groupMemberAddError`, `groupMemberAlreadyInGroup`, `groupMemberRemoveError`, `groupDeleteError` and `expenseDeleteError` are reused, and no ARB key is added or retired.
  - (f) Realtime: same channels, same events. The checker bumps and checker deletes now reach other clients only on commit, so a rolled-back write announces nothing.
  - (g) Test seams: the Dart signatures do not change, so `GroupMembersPage`'s `addMemberOverride`, `previewRemovalOverride`, `removeMemberOverride` and `notifyOverride`, and `PaybackDetailSheet`'s `ExpenseDeleter`, keep their exact function types. No new widget seam is added.
  - (h) Migrations: one new file, supabase/migrations/<timestamp>_group_write_rpcs.sql, timestamped later than the newest migration present at build time; no applied migration is edited. It is authored, not applied, and an entry goes into docs/ristretto/manual-checks.md. No client-side legacy fallback for these new RPCs: no `isMissingFunctionError` gating, and no multi-statement path is kept. Until the migration is applied, the four writes fail with the existing error snackbars, so it must be applied before a release carries this build. (Roadmap header; manual-checks rule; Jakob in prep code-review-2026-10 (2026-10-24).)

## Approach
- Strategy: one migration carrying four plpgsql functions in the house shape of `save_group_all` and `pay_back`: `public.`-qualified, `public."group"` quoted, implicit invoker, `perform public.update_group_member_shares(...)` for the recalc. `remove_group_member` takes the advisory lock and the two `share` table locks, reads the balance and history, returns `blocked` before any write, otherwise stamps or deletes, then recalculates and returns. `add_group_member` follows the same pattern as `save_group_all`'s member loop, for one email, returning which branch it took. The two deletes are today's statements moved server-side, with the null-expense-id recalc on expense delete. On the Dart side, each method shrinks to building params, one RPC call, and parsing the answer. The pure params and parse functions carry the unit tests, the way `payBackRpcParams` already does. Write the migration and its source-shape tests first, then the parameter-name cross-check, which reds until the Dart seams exist. Callers and widgets stay untouched, so the existing seam tests guard the UI.
