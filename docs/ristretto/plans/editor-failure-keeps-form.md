# editor-failure-keeps-form

## Spec
- Source: idea — code review 2026-10-22 (research/code-review-2026-10.md), finding 1 (+ finding 10); research As-is lines tagged "for editor-failure-keeps-form"
- Goal: When saving or deleting an expense fails, the user stays in the editor with everything they typed, is told why and can retry. Only a successful write closes the editor.
- Why: group members using the app · noticed by: a failed save or delete no longer throws away the form, a retried payback no longer double-records, a joining guest no longer rewrites history outside the group

## Contract
- Acceptance:
  - [auto] A failed save leaves the editor on screen (the route behind it is not shown), raises the `expenseCreateError` SnackBar, never shows a check, and returns the CTA to idle (no spinner) so the user can retry. The never-a-check half is already enforced by `a failed save shows the error and never shows a check` in test/widgets/expense_save_status_test.dart (must stay green); the rest is new.
  - [auto] A retry after a failed save sends exactly what the user typed. The second write carries the same form values and the same conversion as the failed first attempt: a user-edited name and amount, and for a foreign entry currency the entry currency, the typed rate and the rate date. Each tap issues exactly one write.
  - [auto] If the write succeeds but remembering the typed rate (`StickyRateNotifier.setStickyRate`) throws, the save still counts as done: the check shows, the editor closes onto the route behind it, the write ran exactly once and no error SnackBar appears.
  - [auto] The successful-save path does not change: a spinner while in flight, one write however often the busy CTA is tapped, the check on the CTA before the pop, no success SnackBar, and the pop after the hold. Already enforced by test/widgets/expense_save_status_test.dart (`the CTA spins while the save is in flight`, `a second tap while busy does not fire a second write`, `the check lands on the CTA before the route pops`, `no "Expense created!" snackbar — the check replaced it`, `the route still pops once the confirmation has been seen`); these must stay green.
  - [auto] A failed delete closes the confirmation dialog and leaves the editor on screen with the user's unsaved edits still in the form: a name changed before tapping delete is still shown, and a following save sends it. It raises the `expenseDeleteError` SnackBar and leaves the header delete action enabled for a retry.
  - [auto] A confirmed delete that succeeds calls the deleter exactly once with the expense's own id and group id, raises the `expenseDeleteSuccess` SnackBar, and leaves neither the dialog nor the editor on screen (the route behind is shown).
  - [auto] While a confirmed delete is still running, tapping the header delete again or the save CTA starts no second write of either kind. When the delete then succeeds, the editor closes once and the route behind it stays on screen.
  - [auto] Cancelling the delete confirmation, or dismissing it with a barrier tap, deletes nothing: the deleter is never called and the editor stays. The cancel half is already enforced by `the editor warns on a settled expense, and cancel writes nothing` in test/widgets/expense_editor_delete_guard_test.dart (must stay green). The dismiss half is new.
  - [auto] After a failed save or a failed delete on a form with unsaved edits, closing the editor still asks the user to confirm discarding them. The failure does not bypass the discard guard.
  - [auto] `dart format`, `flutter analyze` and `flutter test` pass.

When null, the editor calls `ExpenseRepository.delete`.
  - `typedef ExpenseDeleter = Future<void> Function(String expenseId, String groupId)`: same signature, new home in lib/pages/expenses/data/expense_deletion_impact.dart (beside `GroupPaybackLoader`). `PaybackDetailSheet` and `showPaybackDetailSheet` keep using it from there (payback_detail_sheet.dart already imports that file).

- Decisions:
  - A failed save keeps the editor open with every typed value intact, puts the CTA back to idle and shows the error SnackBar, never a check. This keeps the save-status-rollout acceptance (research/code-review-2026-10.md summarises it as "a failed write keeps its SnackBar, CTA back to idle, never a check"). Sources: Jakob in prep code-review-2026-10 (2026-10-24); research/code-review-2026-10.md; save-status-rollout.
  - The success path stays as it is: the check on the CTA, `Motion.saveConfirmationHold` through `reducedIfNeeded`, then the pop. Sources: Jakob in prep code-review-2026-10 (2026-10-24); save-status-rollout.
  - A failed delete closes the confirmation dialog, leaves the editor open with its input intact and shows `expenseDeleteError`. A successful delete ends as it does today: `expenseDeleteSuccess` is shown and both the dialog and the editor are gone. Deletes keep a SnackBar rather than a check because no CTA survives the confirmation (save-status-rollout). Sources: Jakob in prep code-review-2026-10 (2026-10-24); research/code-review-2026-10.md.
  - If persisting the sticky rate fails after a successful write, the save is not a failure: it still goes to done and pops, and the error is only logged (`debugPrint`). Today this case raises "Error while creating expense!" after the write has committed, which invites a duplicate; once failures keep the form open it would invite one for certain. The sticky rate is still remembered only after the write succeeds and only for a user-origin rate (ordering unchanged, multi-currency-expense-rate). Source: Jakob in prep code-review-2026-10 (2026-10-24).
  - "Write, then pop only on success" is ONE private helper on `_ExpenseDetailState`, used by both save and delete. It is lifted out of the current code, not written twice. It runs the write. If the write throws, it logs the error, returns the caller's in-flight state to idle (the save CTA to idle, the header delete re-enabled), shows the caller's error SnackBar and stays. If the write succeeds, it runs the caller's success step, then, only while the editor is still mounted, sets `_bypassDiscardGuard` and pops the editor. Source: Jakob in prep code-review-2026-10 (2026-10-24).
  - `_bypassDiscardGuard` is set only on the success path, immediately before the pop. Today both `finally` blocks set it on failure too (research/code-review-2026-10.md As-is), which is what would make a later close silently drop the form once a failure stops popping. Source: follows from the ruling above.
  - The delete confirmation dialog only asks. It resolves to whether the user confirmed and closes itself; the delete write then runs on the editor through the shared helper. A cancel, a barrier dismiss or a null result never deletes. This is the shape payback_detail_sheet.dart's `_confirmDelete` already has (payback-row-delete), and it is what lets one helper serve both writes. It stays the existing `AlertDialog` with today's title, message and actions (the delete-guard tests find it by type and text); it does not switch to `showDeleteConfirmationSheet`. The end state of a successful delete is unchanged. Sources: payback-row-delete; expense-delete-settled-guard.
  - Single flight across both writes: neither write starts while the other is in flight. Save keeps its `_saveStatus` guard. While the delete write runs, the header delete action keeps showing progress and ignoring taps, extending the existing `_deleteProbeInFlight` window (expense-delete-settled-guard). A save tap while the header delete shows progress does nothing, and a header-delete tap while the save CTA is spinning or showing its check does nothing. The check runs before any state flips, so a refused start leaves the CTA and the header exactly as they were. This matters because the delete write used to run under the modal dialog and now runs with the editor uncovered, and each successful write pops. Source: follows from the dialog ruling above; expense-delete-settled-guard.
  - Delete seam: `ExpenseDetail.deleteExpense` (`ExpenseDeleter?`), null → `ExpenseRepository.delete`, following the precedent of `PaybackDetailSheet.deleteExpense` (Jakob in prep code-review-2026-10 (2026-10-24)). The typedef moves to lib/pages/expenses/data/expense_deletion_impact.dart so that expenses/presentation does not import groups/presentation ("presentation may import data, not the reverse", payback-row-delete review lean).

## Approach
- Today both writes end in a `finally` that pops whenever the editor is still mounted, so the only fix that holds is structural: a failure must have no route to `Navigator.pop`. One private helper on `_ExpenseDetailState` owns the rule "run this write; on a throw, reset the caller's in-flight state, show this error and stay; on success, run this step, then pop the editor with the discard guard bypassed".
- `_saveExpense` keeps its validation gates and the busy flip outside the helper and hands it the `saveExpense ?? ExpenseRepository.saveAll` call. Its success step is the sticky-rate write in its own try/catch, followed by done and the hold.
- The delete dialog stops writing. It returns whether the user confirmed and closes itself. `_openDeleteItemDialog` then passes the `deleteExpense ?? ExpenseRepository.delete` call to the same helper, with the success SnackBar as its success step. The SnackBar is shown before the pop, so it lands on the screen behind (the app's one ScaffoldMessenger is an ancestor of the editor route), exactly as payback_detail_sheet.dart does it.
- Order: the seam first (no behaviour change). Then the helper with the save path, where the five existing save-status tests are the regression net. Then the delete on top of the helper. The renames come last because they change nothing observable.
- Tier: normal — the helper's shape, its single-flight interplay with `_saveStatus` and `_deleteProbeInFlight`, and the two-route delete tests leave real choices for a planner.
- Likely touchpoints: lib/pages/expenses/presentation/expense_detail.dart, lib/pages/expenses/data/expense_deletion_impact.dart, lib/pages/groups/presentation/payback_detail_sheet.dart, test/widgets/expense_save_status_test.dart, test/widgets/expense_editor_delete_guard_test.dart
- Depends: —
- Parallel-with: payback-atomic-recalc, guest-merge-rpc, group-model-parse-safety, expense-search-escape (disjoint files). scan-total-applies, typed-expense-draft, notification-context-free and expense-editor-split all edit expense_detail.dart, so this one does not run in parallel with them.
